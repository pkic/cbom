# Your supplier sent a CBOM. Now what?

Participant pack. Nordhaven Netz is fictional. Documents A and B describe real open-source products
(Keycloak 26.7.3 and nginx 1.27.0), condensed from the working group's examples. A few Keycloak
values are still being verified in that example and are rechecked before printing. Document C
describes a fictional protection relay; its values are illustrative.

## The company

**Nordhaven Netz** is a regional electricity distribution operator in the EU, serving 1.2 million
customers. It is an essential entity under NIS2. Three of its systems matter today.

| System | What it does | Supplier document |
|---|---|---|
| **Identity** | Keycloak runs single sign-on for staff, contractors and the customer portal. Forty internal applications accept the tokens it signs | A |
| **Customer portal edge** | nginx terminates TLS for the customer portal and is administered over SSH | B |
| **Substations** | Sixty substations use the PR-500 protection relay from Vendor C. The relays expect to run until at least 2040. Substation refurbishments are scheduled in 2028 and 2033 | C |

## The task

The board has asked for a post-quantum migration plan by the end of the second quarter of 2027. The
national authority expects high-risk systems to be migrated by the end of 2030, following the EU
coordinated roadmap.

Your team is the migration team. You have the three supplier documents below and nothing else.
In the next hour:

1. **Fill in the plan sheet** for each system. Choose an action for each interface or group of
   interfaces, a timing, what the action depends on, and how confident you are.
2. **Write a gap card** for every question the documents cannot answer. One question per card. Say
   which document it concerns, who could answer it (the supplier, you, a standards body, nobody
   yet), and whether it blocks a decision.

**The six actions:**

| Action | Meaning |
|---|---|
| **Enable now** | The capability exists; switch it on by configuration |
| **Software update** | The capability arrives with a new release |
| **Replace** | No update path reaches it; replace the product or device |
| **Shield** | Carry the protection elsewhere: a tunnel, a gateway, segmentation |
| **Accept and revisit** | Take no action now; set a review date |
| **Escalate** | Ask the supplier for a commitment or for information |

## Document A: identity platform, Keycloak 26.7.3

Produced by the supplier against a **PQC migration profile** (the draft baseline and extended
depth). The subject is the container image, `quay.io/keycloak/keycloak:26.7.3`.

**Thirteen interfaces, in brief:**

| Interface | What it protects | Uses now | Quantum-safe option | Blocked by | Notes |
|---|---|---|---|---|---|
| `tls-https`, `tls-mgmt` | Main listener and health/metrics port | TLS 1.2 and 1.3, X25519, operator's certificate | Planned | **Provider** (Java runtime) | Hybrid ML-KEM groups ship in JDK 27; backports announced. Inherited by all seven TLS interfaces |
| `int-db`, `int-ldap`, `int-broker`, `int-smtp` | Outbound connections to the database, directory, external identity providers and mail server | As above | Planned | **Provider** | The far end must support the hybrid groups too |
| `svc-oidc` | ID and access tokens | RS256 signature with the realm key; no token encryption | ML-DSA committed upstream | **Standard** (JOSE representation still an Internet-Draft) | Roadmap: Keycloak issue 43690. ML-DSA-signed tokens exceed the 4 KB browser cookie limit. Several realm keys can be active at once |
| `svc-saml` | SAML assertions | RSA-SHA256 with the realm key | Under evaluation | **Standard** | |
| `svc-broker-tokens` | Verifying tokens from external identity providers | Whatever the provider signs with | Under evaluation | **Standard** | |
| `mgmt-admin` | Administration, and creating and importing realm keys | Bearer token over TLS | Under evaluation | **Standard** | Cannot generate an ML-DSA key today |
| `int-cache` | Cluster transport between nodes | TLS 1.3, mutual, RSA-2048 key generated by Keycloak, rotated every 30 days | Not available | **Product** | The key type is fixed by the product |
| `sto-realm-keys` | Realm keys and the cluster key, held in the database | Stored **without wrapping** | Not planned | — | |
| `svc-http` | Plain HTTP, port 8080 | **No cryptography** | — | — | Off by default in production mode; often used behind a TLS-terminating proxy |

**Also stated:**

- Validated mode uses an opt-in Bouncy Castle FIPS module. Whether new capability will work in
  validated mode is a certification question.
- The implementing libraries are named: the Red Hat build of OpenJDK 21, and `keycloak-services`
  26.7.3.
- The coverage statement says every externally reachable interface is declared.
