GROUP

Change planning: a richer document, a shared core

Use cases whose profile adds facts the baseline does not have: capability per cryptographic purpose, what blocks it and who can clear it, what enabling it requires, and whether the far end can still be classical. The orientation is both: what the product uses today and what it could use. A document produced against the baseline alone cannot be evaluated against these profiles at all.

The grouping and the change core are proposed in draft decision 0023 and are not yet settled.

The change core

The profiles in this group share most of what they ask for. A profile has a single base, so a fact two of them need has to sit in a common ancestor rather than be defined twice. That ancestor is the change core.

  • In the core: capabilityStatus, blockedBy and roadmapRef per purpose; the Supported forms of the algorithm attributes; enablementMethod and providerLocation; coexistence and negotiationControl; integrationConstraints; keyWrapping and keyWrappingSupported.
  • In the core as conditional rules: updateMechanism, updateAuthority and keyReplaceable, which apply only to update interfaces. The IoT and substation profiles need them. A product with no update interface does not have to supply them.
  • Not in the core: what each profile adds for its own subject, shown in the last column of the table below.

The core is published as a sibling of the PQC migration profile. It declares each shared rule under the id that the migration profile already uses, so no rule id changes. Whether the core is specific to a post-quantum target or neutral about the target is open (Q66). If it is neutral, crypto-agility assessment needs no profile of its own.

The use cases in this group

PQC migration

An operator has to decide which systems to migrate, in what order, and what each will cost. To do that, it has to separate three kinds of system: those that need only a configuration change, those that need a software update, and those tied to hardware that must be replaced. The consumers are migration programme leads and, increasingly, the regulators they report to.

A profile for this purpose requires the algorithms an interface uses today and the algorithms it is able to use, so that the two can be compared. It also requires the lifecycle stage, which says which of the two is being reported. It does not ask for a readiness verdict. That judgement depends on criteria that change over time, so it belongs in an external policy. This use case is developed in detail on the PQC Migration tab.

IoT device estates

An operator of a large deployed estate of constrained devices decides, per device model, whether the cryptography can be changed in place, whether the device has to be replaced, whether something in front of it can carry the cryptography instead, or whether the exposure is accepted and documented. Scale changes the problem. Each action costs the unit price multiplied by the number of devices deployed, plus the cost of reaching each one physically.

Three things make this more than a sector version of the first entry. A capability answer of no can be permanent, because the limit is available flash or a frame size fixed by a radio standard rather than a decision somebody could take differently. The party able to install new firmware is often neither the manufacturer nor the operator. And the document describes a device model, while the decision is made about the deployed instances of it. The producer cannot state the things that vary per instance, so the operator has to add them from its own records. A profile for this purpose therefore needs attributes that none of the others need: whether an update mechanism exists, who can trigger it, and whether key material fixed at manufacture can be replaced at all. This use case is drafted on the IoT Device Estate tab, where the choice of consumer is still open.

Substation automation (OT)

A grid operator plans the migration of one substation automation system. For each communication path, it chooses one of four actions. It can migrate the path in place. Where the messages are already protected with symmetric cryptography, it can migrate only the key plane. It can carry the path on a conduit. Or it can replace the device at its next refurbishment. Protection messages have a 3 ms time budget and cannot carry a post-quantum signature. The exposure is in group key distribution, certificate enrolment and firmware verification instead.

Two things distinguish it from the first entry. The subject is a system assembled by an integrator from several suppliers' products, so it needs a component profile and a system overlay. And the cost of a change includes re-certification. Drafted, with illustrative values, on the Substation Automation page.

Crypto-agility assessment

Before an algorithm needs replacing, an architecture or risk function wants to know how hard replacing it would be. The answer is rarely the same across an estate. Where an assessment has been done, the interfaces that will cause trouble can usually be found in advance.

The deciding factor is whether the cryptography sits in a provider that can be replaced, or is fixed in place. That makes the implementing library and its location the central attributes. It also matters that key exchange, encryption and authentication are separate attributes rather than one cipher-suite string, because each of them is usually agile to a different degree.

PKI and certificate estate migration

A PKI owner decides which hierarchies and certificate profiles move to post-quantum algorithms, in what order, and whether to run a parallel or a composite hierarchy while relying parties catch up. The deciding fact is one that no other profile asks for: whether the relying parties that validate a given certificate population can process the new algorithms at all.

The subject is a system, not a product: certification authorities, registration and validation services, the HSMs that hold the keys, and the populations they serve. Proposed.

Code and firmware signing migration

A publisher of software or firmware decides when it can move its signing keys to a new algorithm. Its own signing service is not the main constraint. The verifiers already deployed are. A boot ROM that verifies one algorithm with one fixed key decides the timetable for every device that carries it.

It shares the update-path facts with the IoT and substation entries, which is why those facts belong in the change core rather than in any one profile. Proposed.

Shared-trust network migration

The operator of a closed network with many participants, such as a payment or settlement scheme, decides whether and when every participant can move to a new shared trust anchor. No participant can move alone, and the slowest participant sets the date.

The baseline describes two-party relationships and cannot describe this yet. It is blocked on the multi-party trust model in the design note of the same name. Proposed.
