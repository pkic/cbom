USE CASES

Use cases

A CBOM profile is written for someone who has a decision to make. A use case names that person and that decision: a buyer comparing tenders, a responder tracing an advisory, a grid operator planning a migration. The use cases the working group has identified are collected here. The most developed ones are taken further: each is turned into a profile, the profile is applied to a product or a deployment, and the resulting documents are evaluated against it.

Use case groups

Use cases are split into four groups. Two are defined by the facts a profile asks for. In Disclosure, the goal is to know what cryptography a product uses. In Change planning, the goal is to decide how to change it. The table below compares these two. The other two are defined by who handles the document. In Operation, the operator of a system produces it. In Assurance, the reader relies on it as evidence. The Operation group has its first profile, Deployment Disclosure v0.2.

Disclosure: know what a product usesChange planning: decide how to change it
The profile chooses which facts a CBOM must carry from the set every CBOM already describes: interfaces, protocols, algorithms and the libraries that implement them. The profile adds facts a basic CBOM does not have: what each interface could support, what is blocking it, and what changing it costs.
One CBOM from a supplier can answer every profile in this group. A supplier has to produce a richer CBOM. That CBOM then answers the disclosure profiles as well.
Procurement, supply-chain transparency, vulnerability response, due diligence. PQC migration, IoT device estates, substation automation, crypto-agility.

Use cases are not grouped by sector. A telecom operator and a grid operator planning a migration make the same kind of decision, so they share a use case. Terms specific to a sector go into the profile, not into a separate use case.

What is not a use case

Two things are often suggested as use cases. Both are ways of applying a profile instead.

  • Continuous integration quality gate. A pipeline fails a build when a CBOM does not conform. Any profile can be applied this way. What the gate needs is a validator that returns a usable exit status and report. The reference validator, validate_cbom.py, exits with 0 when a document conforms and 1 when it does not conform. A gate must not treat every non-zero code as a failure: exit code 4 means the document was refused on its carrier version and never evaluated. This is covered in Conformance and the Demo.
  • Change impact between versions. Comparing two CBOMs of the same product to see what changed. This is a comparison between two documents. It is covered in Versioning.

How this section relates to the methodology

The methodology is the working group's deliverable. It says how to define a profile, and Starting from a use case explains why every profile begins with a consumer and a decision. The methodology illustrates its concepts with the Keycloak 26.7.3 example. It does not list any use cases. Everything about particular use cases, including the worked examples, is in the Use Cases section.

The methodology and the worked examples use the same eight published profiles: Interface Enumeration v0.4, the Interface Disclosure Baseline v0.10, Deployment Disclosure v0.2, PQC Migration v0.8, PQC Migration Extended v0.2 (a deeper level of PQC Migration), Procurement v0.2, Change core v0.1 and PQC Migration for substation components v0.1. Every choice in the consolidated baseline is provisional. The rules files and the Keycloak and protection IED examples are under Files.
