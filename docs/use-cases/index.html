USE CASES

Use cases

A CBOM profile is written for someone who has a decision to make. A use case names that person and that decision: a buyer comparing tenders, a responder tracing an advisory, a grid operator planning a migration. This section collects the use cases the working group has identified, and takes the most developed of them through to a profile, a real product and documents that can be checked.

Four groups

Use cases fall into four groups. The first two differ in what the profile asks for, which matters most to whoever has to produce the CBOM. The other two differ in who produces the document and who relies on it.

GroupWhat sets it apartWho produces the CBOMExamples
Disclosure
know what a product uses		The profile chooses which facts a CBOM must carry from the set every CBOM already describes: interfaces, protocols, algorithms and the libraries that implement them. One CBOM from a supplier answers every profile in the groupThe supplierProcurement, vulnerability response, due diligence
Change planning
decide how to change it		The profile adds facts a basic CBOM does not have: what each interface could support, what is blocking it, and what changing it costs. That richer CBOM answers the disclosure profiles as wellThe supplierPQC migration, IoT device estates, substation automation (OT)
Operation
describe what is running		The operator states facts no supplier knows: what data crosses an interface, how long it must stay confidential, what was actually negotiated, what changed since the last report. It cites the suppliers' CBOMs rather than repeating themThe operatorHarvest-now-decrypt-later exposure, migration progress, managed services
Assurance
rely on it as evidence		The reader is an auditor or regulator who cannot ask follow-up questions. The facts are usually the disclosure facts; what is added is proof of when, from what and by whom the document was made, and that it is still currentSupplier or operatorCompliance reporting, certification evidence

Disclosure and change planning are defined in draft decision 0023; operation and assurance were added as an amendment and are less settled. A use case is not grouped by sector. A telecom operator and a grid operator planning a migration make the same kind of decision, and sector terms go into the profile, not into a separate use case.

What is not a use case

Two entries are often suggested as use cases and are ways of applying a profile instead.

  • Continuous integration quality gate. A pipeline fails a build when a CBOM does not conform. Any profile can be applied this way; what it needs is a validator with a usable exit status and report, covered in Conformance and the Demo.
  • Change impact between versions. Comparing two CBOMs of the same product to see what changed. That is a difference between documents, covered in Versioning.

How this section relates to the methodology

The methodology is the working group's deliverable. It says how to define a profile, and Starting from a use case explains why every profile begins with a consumer and a decision. It illustrates its concepts with a small nginx example and lists no use cases. Everything about particular use cases, including the worked examples, is in this section.

The worked examples use the draft profiles of decision 0022 (interface disclosure baseline v0.8, PQC migration v0.7 and its extended depth). The methodology still describes the published versions (v0.7 and v0.6). The two will match once the drafts are adopted.
