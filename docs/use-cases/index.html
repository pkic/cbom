USE CASES

Use cases

A CBOM profile is written for someone who has a decision to make. A use case names that person and the decision. Examples are a buyer comparing tenders, a responder tracing a security advisory, and a grid operator planning a migration. This section lists the use cases the working group has identified so far. For the most developed ones, it goes further: it shows the profile, applies it to a real product, and includes documents that can be checked against the profile.

Four groups

The use cases fall into four groups. The first two groups differ in what the profile asks for. This matters most to whoever has to produce the CBOM. The other two groups differ in who produces the document and who relies on it.

GroupWhat sets it apartWho produces the CBOMExamples
Disclosure
know what a product uses		The profile chooses which facts a CBOM must contain. It chooses them from the facts that every CBOM already describes, such as interfaces, protocols, algorithms and the libraries that implement them. One CBOM from a supplier can answer every profile in this groupThe supplierProcurement, vulnerability response, due diligence
Change planning
decide how to change it		The profile adds facts that a basic CBOM does not contain. For each interface, it asks what the interface could support, what is blocking it, and what a change would cost. This richer CBOM can also answer the disclosure profilesThe supplierPQC migration, IoT device estates, substation automation (OT)
Operation
describe what is running		The operator states facts that no supplier can know. Examples are what data crosses an interface, how long that data must stay confidential, which algorithms were actually negotiated, and what has changed since the last report. The operator's document refers to the suppliers' CBOMs instead of repeating themThe operatorHarvest-now-decrypt-later exposure, migration progress, managed services
Assurance
rely on it as evidence		The reader is an auditor or a regulator who cannot ask follow-up questions. The facts are usually the same as in the disclosure group. What is added is proof of who made the document, when, and from what sources, and proof that it is still currentSupplier or operatorCompliance reporting, certification evidence

Disclosure and change planning are defined in draft decision 0023. Operation and assurance were added later as an amendment, and they are less settled. Use cases are not grouped by sector. A telecom operator and a grid operator who plan a migration make the same kind of decision. The terms that belong to a sector go into the profile for that sector. They do not need a separate use case.

A worked example has a checked profile, and documents that conform and do not conform to it. A draft worked example has a page in the same shape, but it is not yet settled. A use case that is described has its consumer, its decision and the needs of its profile written down. A proposed use case has only a named consumer and decision. The full definitions are on Proposing a use case.

What is not a use case

People often suggest these two entries as use cases. They are really ways of applying a profile.

  • Continuous integration quality gate. A build pipeline fails a build when a CBOM does not conform to a profile. Any profile can be used in this way. What the pipeline needs is a validator that returns a clear exit status and report. Conformance and the Demo cover this.
  • Change impact between versions. This means comparing two CBOMs of the same product to see what has changed. It is a comparison between documents, and Versioning covers it.

How this section relates to the methodology

The methodology is the working group's deliverable. It explains how to define a profile. Its page Starting from a use case explains why every profile begins with a consumer and a decision. The methodology uses a small nginx example to illustrate its ideas, and it does not list any use cases. Everything about particular use cases, including the worked examples, is in this section.

The worked examples use the draft profiles from decision 0022. These are the interface disclosure baseline v0.8, PQC migration v0.7, and the extended depth of PQC migration. The methodology still describes the published versions, v0.7 and v0.6. The two sections will match once the working group adopts the drafts.
