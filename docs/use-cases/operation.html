GROUP

Operation: the operator describes what it runs

Use cases in which the CBOM is produced by the operator of a system rather than by the supplier of a product. The subject is a deployed system, a service or an estate, and what is reported is mostly configured or observed. An operator can state facts no supplier knows: what data crosses an interface and how long it must stay confidential, what was actually negotiated, which instances are still running, and what has changed since the last report.

Proposed in October 2026 as an amendment to draft decision 0023, which defined the first two groups. The group is not yet settled. Its first profile, deployment disclosure v0.1, is published as part of the consolidated baseline (decision 0025), with two Keycloak deployment records.

What the group shares

The Disclosure and Change planning groups are each defined by the facts their profiles ask for. The Operation group is defined by who produces the document: the operator of the system. The operator can see the whole deployed system. A supplier cannot see how its product is deployed, so supplier profiles only ask for facts that can be known from the product itself. That limit does not apply to an operator, so a profile in this group can ask for more. It can require the deployment facts that the interface disclosure baseline excludes because a vendor cannot know them: the payload an interface carries, its confidentiality lifetime, the number of instances, and the configuration as observed rather than as declared.

An operator document usually draws on supplier documents rather than repeating them. It cites the supplier CBOM for each product it runs, by BOM-Link and SHA-256 hash, and adds what only the operator knows. A document that cites other documents and adds to them is an overlay, as defined in Maturity. The substation system document has the same relation to its component documents.

A use case belongs in this group when the operator produces the document. An operator describing what it runs may also be planning a change. A profile in this group can therefore extend either the interface disclosure baseline or the change core, which is the shared base of the change-planning profiles. Each use case decides which of the two to extend. The first profile, deployment disclosure, extends the baseline.

Worked example: deployment disclosure v0.1

The profile is profile-deployment-disclosure.rules.json, version 0.1. It extends the interface disclosure baseline v0.9. Its consumer is an operator, or an assessor acting for one, responsible for a deployment built from products it did not build. The decision is, for each interface of the deployment: which published weakness affects it, whether what the deployment permits matches what it was seen to do, and where the deployment falls short of what its products can do.

The profile accepts one subject type, deployment, and two stages, configured and observed. It excludes implemented, because a deployment record that repeats the vendor's build facts adds nothing. It cites the vendor's record instead. The vendor writes the product record. The operator writes one deployment record per stage. The records are joined, not merged.

RuleLevelWhat it requires
P1MUSTThe record cites each document it builds on by BOM-Link (urn:cdx:<serial>/<version>) and SHA-256 hash. When the consumer supplies the cited document, the validator checks its serial number, version and hash.
I1MUSTcorrespondsTo: the interface in a cited document that this interface realises, as a BOM-Link to its bom-ref, or the literal no-product-document. The implementing library is inherited across this join. Present-state facts are never inherited.
I2MUST at observedobservationMethod: how each observed value was obtained (active-probe, passive-sensor, endpoint-query, platform-query, inspection).
I3MUST at observedobservedAt: the time or interval of the observation.
R1MUST at configuredA pointer to the configuration revision the record was read from.
R2SHOULD at observedA pointer to the evidence an observed value was taken from. Withholdable, because evidence often carries internal addresses.
R3SHOULDA pointer to the operator's data register, which records what data each interface carries and how long it must stay confidential. Withholdable. The record points to the register and does not carry it.
R4MAYA pointer to the certificate policy of the CA that issues the deployment's certificates.

The examples describe an illustrative operator, Example Org, running Keycloak 26.7.3 at sso.example.org. The operator ends TLS at an ingress (nginx with OpenSSL 3.5) and runs Keycloak behind it with its plaintext HTTP listener enabled. Both records cite the vendor's product record.

The observed record shows two things the configured record cannot. 29% of ingress sessions still negotiate X25519 alone, although the deployment permits X25519MLKEM768. The use cases in this group

Managed and cloud service disclosure

The producer is the operator of the service, so the use case shares this group's premise. Its description is in the Disclosure group, where the register lists it. Proposed.

Stored data and archive protection

Only the operator knows what a store holds and for how long, so the use case shares this group's premise. Its description is in the Change planning group, where the register lists it. Proposed.

Harvest-now-decrypt-later exposure

A security function decides which of its systems are exposed to traffic recorded today and decrypted later, and which to migrate first on that ground. Exposure depends on two facts a supplier cannot state: what data crosses an interface, and how long that data has to stay confidential. Combined with the key establishment the interface uses today, these two facts give the window during which recorded traffic remains worth decrypting.

Some of these facts are known to the supplier, however. Credentials on a management interface and key material on a key-management interface follow from the interface's design, and they often have the longest lifetimes. Q36 asks where the supplier's facts end and the operator's begin. The deployment profile already gives the operator's half a place: rule R3 points to the operator's data register. Proposed. Depends on Q36, Q37 and Q45.

Migration progress over time

A migration programme lead, or a regulator receiving its reports, decides whether a migration is on track: how much has moved since the last report, how much remains, and why the numbers changed. The facts needed are two operator documents about the same estate at different dates, and the reason for each difference between them: an interface migrated, a product replaced, an instance retired, or an earlier finding that turned out to be a false positive.

Comparing two documents is covered by Versioning. This use case adds the reason for each change. Without the reason, a reader cannot tell whether a count fell because work was done or because a scanner stopped looking. Raised in member feedback on the Inventory chapter: "How much more do we have to do to be PQC ready?" Proposed.

The operator's migration register

An operator records, for each finding in its estate, the decision it took: the response, who owns it, the target date and the status. These are judgements and plans. Decisions 0002 and 0007 keep them out of a supplier's CBOM, because a supplier document records facts about a product and a date there is a promise the supplier may not control.

They belong in the operator's own document about its own estate. Documents of that kind are what this group covers. CycloneDX 2.0 gives them a native home in its root risks list, with an owner, a response strategy, a target date and a status for each risk. The validator ignores risks for conformance, and a supplier's product record should not carry them. Proposed.
