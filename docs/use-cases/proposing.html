WRITING ONE

Proposing a use case

This page explains how a use case is added to this section, how it grows into a worked example, and what each status means. Please read it before you copy the template.

When a use case is worth proposing

A use case is worth proposing when you can name a consumer and a decision, and when the interface disclosure baseline does not already require the facts that the decision needs. A sector, a product or a field in a file format is not a use case. If you start from the fields that a format offers, the profile has no stated purpose. Then nobody can judge whether it asks for the right things.

  1. Open a topic on the aspect issues. State the consumer, the actions the consumer is choosing between, and the questions that the decision raises.
  2. Add the use case to the register on the overview and to its group page, with the status proposed. If it does not fit any of the four groups, raise this first. It may need a new kind of profile, or it may not be a use case at all.
  3. Copy the template and work through it from the top. A page that is only half finished is still worth a pull request. The empty sections show the working group which questions it has to answer.

Sometimes an existing profile already serves the use case. Sometimes a depth of an existing family serves it, or the change core alone. Each of these outcomes is better than a new profile, and a proposal should say so when it applies.

Status

StatusWhat it requires
ProposedA consumer and a decision are named, and nothing more. This invites someone to develop the use case. It does not commit the working group to writing a profile for it.
DescribedThe group page describes the consumer, the decision, the limits on what the producer can know, and what the profile would need.
Draft worked exampleA page exists in the eight-part shape described below. Some of the rules, documents or verdicts are not yet settled, and the page says which ones.
Worked exampleThere is a rules file that passes requirements C1 to C17 of Conformance. There is at least one document that conforms to it and one that does not. The validator has checked both verdicts.

The shape of a worked example

Every worked example has the same eight parts, in the same order, because each part feeds the next one. The eight parts are the twelve steps of Method, grouped so that they are easier to read. The template has the same eight parts, left empty.

  1. The decision being supported. Who the consumer is, which actions it is choosing between, and which questions it has to answer to make the choice. Naming the actions makes the rest of the page checkable. If a decision can only be answered in one way, it is not really a decision. A profile written for it has no clear point at which to stop asking.
  2. The constraint the producer is under. What the party who fills in the document can actually see. An operator who runs its own service can be asked for more than a vendor who ships a product that it cannot inspect from the inside. A profile that ignores this difference asks for things nobody can supply.
  3. From questions to attributes. Each question is turned into a fact that can be stated at the boundary of the product. Some questions cannot be turned into such a fact. They matter as much as the others, so they are recorded and not dropped.
  4. The profile definition. The rules for the product, for each interface and for each group, with their conformance levels. This part also lists any inherited rule that the profile makes stricter, and any rule that applies only under a stated condition.
  5. A worked interface. One real interface with every required attribute filled in. This lets readers check the rules against a concrete case.
  6. What the profile deliberately excludes. Each exclusion, with its reason. Without this list, nobody can review the profile properly. A reader cannot tell a deliberate exclusion from an attribute that nobody thought of.
  7. Expressing it in a CBOM. Where each attribute goes in CycloneDX and in SPDX, and which attributes have no native field in those formats.
  8. Recorded decisions and open questions. What was decided while the page was written, and what the working group still has to decide.

Why worked examples are kept out of the methodology

  • The number of examples will keep growing, and the specification should not. If every worked example were part of the methodology, the methodology would grow each time someone added a use case.
  • They have different readers. Someone who assesses the methodology needs one good example. Someone who has to plan a migration needs the full example for their own case.
  • They are maintained differently. Each profile has its own versions and its own maintenance schedule, as Governance describes.
