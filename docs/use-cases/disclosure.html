GROUP

Disclosure: one document, many profiles

In these use cases, the profile selects and tightens facts the interface disclosure baseline already defines. The orientation is inventory: what the product uses today. One document that meets the baseline and names the implementing library can answer every profile in this group. The supplier does not need to reissue it.

The grouping is proposed in draft decision 0023 and is not yet settled.

What the group shares

Every profile here extends the interface disclosure baseline, or is one of its depths. The facts are the baseline's: what the product is, which interfaces it exposes, the protocol and version of each, the algorithms for each cryptographic job, the endpoint roles, the implementing library, the lifecycle stage of the report, and whether the list is complete. A profile in this group chooses which of them are mandatory, removes a permission to withhold, or adds a structural rule about which kinds of interface must be present. It does not add new attributes.

That is what makes one document serve several consumers. A buyer, a vulnerability responder and an acquirer can each apply their own profile to the same unchanged document. The depth ladder in Maturity applies here too. The entry depth asks for fewer of the same facts. It is the right tool when coverage matters more than detail, as in due diligence.

The limit works in one direction only. A document produced only for this group cannot answer a change-planning profile, because the capability facts were never collected. A document produced for change planning answers this group as well.

The use cases in this group

Supply-chain transparency

A supplier at any tier needs to tell its customers what cryptography its product uses, and would prefer to do so once rather than in a different format for each customer. Downstream, an integrator needs disclosures it can compare across suppliers.

A disclosure baseline meets this need. What makes this use case unusual is the upper limit on what may be asked. A supplier must be able to satisfy the profile without exposing information it has a legitimate reason to protect. That is why it matters so much here that an attribute can be marked as withheld, rather than silently left out.

Procurement and tender conformance

An operator states cryptographic requirements in a tender and needs to check what comes back without reading it by hand. Today this is done with security questionnaires, whose answers are prose and cannot be compared between vendors. A profile expresses the requirement in a form a machine can evaluate, and the vendor's CBOM is the response to it.

Some of the requirements are about structure, not only about attributes. Besides a description of each interface, a procurement profile usually requires certain kinds of interface to be present. This is how it catches a vendor that describes its service interface and says nothing about how the product is administered.

Drafted as a worked example on the Procurement page.

Vulnerability management and incident response

An advisory is published against a cryptographic library. The question is which services are affected, and it has to be answered in hours rather than weeks. This use case has the least tolerance for manual work.

Almost everything depends on one attribute: the identifier of the implementing library, expressed in a form that can be matched against a vulnerability feed. Endpoint roles, interface types and lifecycle stages contribute little here. A profile written for this purpose is deliberately narrow.

It is also the only use case in this list that the baseline gets in the way of. That attribute is the one the baseline allows a producer to withhold. Vulnerabilities sets out what a CBOM contributes when an advisory lands, which kinds of weakness it is the only evidence for, and why no profile for this purpose has been written yet.

Mergers and third-party risk due diligence

An acquiring organization, or one onboarding a significant partner, needs a view of cryptographic exposure across an estate it does not operate and cannot inspect directly. The work is usually done under time pressure and with limited cooperation.

Coverage matters more than depth. The assessor needs a broad disclosure across the estate, with missing data recorded as missing rather than left blank. That shows where the risk is concentrated: deprecated algorithms still in use, and cryptography bound to hardware that will not be upgraded.

Service assurance

An assurance team responsible for customer-facing services, including critical communications, needs to know which services a cryptographic weakness or a planned change reaches. The facts about each component already exist in that component's document. What is missing is the mapping from components to the services they carry.

That makes it a system overlay rather than a new set of attributes. An overlay is a document that references the component documents and states which services depend on which interfaces. The use case comes from the telecom sector paper, and it has the same structure as the substation overlay. Proposed.
