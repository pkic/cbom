WORKED USE CASE

PQC migration: from use case to profile

One use case, developed from the decision a consumer is trying to make through to two profile definitions, and applied to one real product throughout: Keycloak 26.7.3, an open-source identity provider. It follows the twelve steps set out in Method and is the reference example for how the remaining use cases are worked up.

Illustrative, and in review. The profiles and example documents follow draft decision 0022, which revises the migration profile to v0.7, adds an extended depth, and states how application-layer interfaces are expressed in CycloneDX. Attribute names are proposals of this example rather than established terms. The Keycloak values are taken from its documentation and issue tracker; the few still to be verified are marked.

The decision being supported

An operator runs a product it did not build and cannot inspect. It needs to answer three questions about every interface that product exposes, and it needs the answers in a form it can aggregate across hundreds of instances.

  • Can this interface be made quantum-safe at all, and if so with which algorithms?
  • What would it take: a configuration change, a software update, or new hardware?
  • What breaks when we do it, and can we do it while the other end is still classical?

None of these is an inventory question. Knowing which algorithms an interface uses today leaves all three unanswered, because they concern capability, the route to enabling it, and what enabling it costs in interoperability. A migration profile therefore has to require the facts those answers rest on.

For Keycloak the operator is typically an enterprise running it as the single sign-on service for its applications. Every relying party trusts the tokens it signs, so its migration decides the timetable of many other systems as well as its own.

The black-box constraint

The defining constraint is that the consumer cannot see inside the product, and the vendor will not expose its internals. Everything the profile asks for therefore has to be declarable at the boundary: observable at an interface, or stated by the vendor as a property of the product it ships. Anything requiring disclosure of source, design or internal architecture is out of scope, and would not be supplied in any case.

This is also why the profile is interface-driven rather than product-driven. A single answer at product level, of the kind "this product supports ML-KEM", is not actionable: a product may support a post-quantum key exchange on its service interface and not on its management interface, and the operator has to migrate both. Migration is planned and executed one interface at a time.

The worked product: Keycloak 26.7.3

Keycloak is a useful subject because its most important cryptography is not TLS. It is the signature on every token it issues, which every relying party verifies. That signature migrates on a different timetable from the TLS underneath it, and depends on a different standard. A migration profile that could not tell the two apart would fail on the first product it met.

Three more properties make it instructive. Its TLS key exchange comes from the Java runtime rather than from Keycloak, so the blocker belongs to a provider. It generates the key for its own cluster transport, so one key type is fixed by the product. And it stores its realm keys in its database without wrapping them, which makes a storage interface part of the picture.

The subject is the container image, quay.io/keycloak/keycloak:26.7.3, at its defaults. The image fixes the Java runtime, and with it the TLS capability. The ZIP distribution runs on whatever runtime the operator installs, so its TLS capability is a fact about a deployment and belongs in a separate document.

Thirteen interfaces result. The seven TLS interfaces all use the Java runtime's providers; the four application-layer interfaces are implemented by Keycloak itself.

Two profiles, two depths

Keywords follow BCP 14. Both profiles are product-independent: no rule names a product, a vendor or an interface instance. Attribute names follow the conventions in Method: keyExchange and authentication denote what the interface uses now, and the Supported suffix denotes what it is able to use.

The questions split into two groups. The first is about the interface: what it does, what it could do, and what stands in the way. The second is about what surrounds the interface and has to move with it or before it: the surface that must create the new key, the store that must hold it, and the services it depends on. A supplier can usually answer the first today. The second asks for information many cannot yet give. Putting both in one profile would set the entry bar where few could reach it, so the use case is served by a family of two, ordered by depth (decision 0019).

The one tightening

Inherited ruleBaselineHere
I9 implementationPurlMUST, withholdableMUST, not withholdable

Migration planning depends on knowing which library implements an interface, since that determines whether an update exists and when it arrived. A vendor withholding it leaves the consumer unable to sequence the work. This is the only inherited rule this profile changes, and raising a level is permitted because it tightens.

Conditional rules

Several rules apply only in certain states. A profile is not limited to a flat list of mandatory fields; a requirement can depend on the value of another attribute. I5 obliges a producer claiming that a capability needs a software update to say which version provides it. I11 asks for a certificate reference only where a validation scheme is declared, and I12 asks for wrapping algorithms only on a storage interface. Inside the capability group, G1.2 asks for a blocker only where a purpose is not available, and G1.4 asks about validated mode only where it is. The unconditional alternatives are unhelpful: requiring a version or a certificate from every interface produces noise, and requiring none leaves the useful case unstated.

Availability, and why it is not a date on an interface

An earlier draft of this profile put a plannedAvailability date on each interface. It is the obvious design, and it does not hold up. The reason is structural.

Interfaces do not gain capability independently. A product with six TLS interfaces built on one cryptographic provider gains post-quantum key exchange on all six at the moment that provider is updated and the product integrates it. A date on each interface duplicates one underlying event six times, and the six copies drift apart as they are maintained. Availability belongs to the change that delivers the capability; the interfaces merely inherit it.

What a planner needs first is therefore not the date but the obstacle, because the obstacle determines whether any date is credible and who is able to move it.

blockedByWhat has to happenWho can move itPredictability
providerA dependency is upgraded to a version offering the algorithm.The vendor, by taking the upgrade.Reasonable
productThe product's own code must change to expose or negotiate it.The vendor, in a named release.Reasonable
hardwareA module, firmware or platform must support the algorithm.The vendor together with the module supplier.Poor
standardNo specification yet defines the algorithm for this protocol.Nobody, until the standards process concludes.None
certificationA validated implementation is required, for example under a scheme such as FIPS.An external laboratory or scheme.Externally determined

The distinction that matters most is the fourth row. An interface blocked on a protocol standard cannot be given a credible date by any vendor, and a consumer who understands that stops waiting and considers compensating controls instead. Recording it as "planned, date to follow" alongside a case that is genuinely scheduled for the next release conflates two situations that call for opposite responses.

Keycloak shows four of the five on one product. TLS key exchange is blocked by the provider: hybrid ML-KEM groups ship in JDK 27 and are enabled there by default, with backports to earlier releases announced, so the date is the runtime's. Token signing is blocked by a standard: an ML-DSA signature provider is committed upstream, but the JSON Web Key representation it needs is still an Internet-Draft. The cluster transport is blocked by the product, because Keycloak generates its RSA-2048 key itself. And whether the capability will be usable in validated mode is a certification question for the Bouncy Castle FIPS module.

Where a date or release is offered, the profile keeps it out of the interface and out of the CBOM. Target release and date sit in a roadmap entry that interfaces reference through roadmapRef, so that interfaces sharing a blocker point at one entry. Two reasons: a CBOM revision is an immutable point-in-time record, so a slipping date either goes stale inside an authoritative-looking document or forces CBOM republication when nothing about the product has changed; and roadmap data has a different owner and a different cadence from the rest of the document, which is the same argument the Governance section makes for keeping separately-lifecycled artifacts apart.

A target release is also preferable to a calendar date. Releases are the vendor's own unit of change, and the statement "this lands in 9.x" survives slippage in a way that a date does not.

Three existing parts of the methodology carry this without additions. Forward-looking capability is carried by capabilityStatus, blockedBy and roadmapRef, not by the lifecycle stage. This profile accepts only implemented, configured and observed, so an interface may not report its present state as intended: a migration plan built on cryptography a producer intends to implement is a plan built on an intention. The stage says how the reported present state was obtained; the three attributes above say what is coming. A vendor that shares roadmap detail only under agreement records roadmapRef as withheld, which is more informative than an empty field. And the freshness policy in Versioning applies to the roadmap entry, so a consumer can tell a current commitment from one nobody has revisited.

Capability, per purpose

Capability is stated per cryptographic purpose, because the purposes of one interface migrate on different timetables. Across Keycloak the two purposes that matter most look like this.

The other five purposes carry a status as well. On the TLS interfaces, encryption, data integrity and key derivation are available, and each says whether it works in validated mode. Key protection is not-planned everywhere, which is the storage finding again: nothing wraps Keycloak's keys at rest. A deferred purpose owes only a status and, where it is not available, a blocker. That costs a producer almost nothing, and it keeps a staged profile from becoming a permanent floor.

Most of these values are the same across interfaces because they belong to the implementation. The document states them once, on the library that provides the interfaces, and an interface states only what differs. The cluster transport inherits the JDK's entries and overrides entity authentication; SAML inherits Keycloak's and overrides two purposes. Rules are evaluated on the resulting values.

A purpose is not an operation, and the distinction is what makes the vocabulary worth having. CycloneDX already records operations: a certificate signature carries cryptoFunctions: ["sign", "verify"], and so would a firmware signature on the same product. One is entity authentication that migrates when the PKI does; the other must still verify years after it was written. Same operation, different decade, different work. See Terms for the four-part test an entry has to pass, and decision 0010 for the reasoning.

What a planner concludes

Without seeing inside the product, an operator reading the baseline document can conclude the following. No Keycloak interface can be made quantum-safe by configuration today. TLS key exchange arrives with the Java runtime, so the action is to track the runtime in the image and to test hybrid groups against the directory, the database and the mail server, which must support them too. Token signing is the long pole: it waits on a standard, so pressing the supplier for a date will achieve little, and the time is better spent finding relying parties that reject unknown key types and flows that keep tokens in cookies. The cluster transport depends on a change in the product. Plain HTTP behind a proxy carries tokens in clear on the internal hop and should be closed first, because no post-quantum work protects traffic that is not encrypted at all. An inventory of the algorithms in use today yields none of these conclusions.

The extended document adds three conclusions to the baseline's. When ML-DSA signing lands, the key management surface must be able to generate the key as well, and today it cannot: every baseline rule passes and the operator still could not migrate, which is the case pqc-migration-extended#I3 exists for. TLS migration cannot start until the operator's certificate authority can issue the new certificates, and the directory and identity providers have to follow. And the realm keys that sign every token sit unwrapped in the database, so a database backup is as sensitive as the signing service itself.

What the profiles deliberately exclude

The profile omits three kinds of information, in each case deliberately.

It carries no readiness or posture verdict. Whether a declared algorithm set counts as quantum-safe is a judgement against criteria still under revision, so an external policy computes it from these facts at the time of asking and dates the result. Policy Evaluation sets out the reasoning, which is also why pqcPosture was dropped from the baseline profile.

Maturity scores are excluded on the same grounds. Collapsing heterogeneous attributes into one number has a further drawback: it tends to hide whichever attribute is actually blocking the migration.

Internal implementation is out of scope, so no source references, design detail or component structure are requested. This follows from the black-box constraint and is not a concession to it. A vendor asked to expose internals will decline, and a profile nobody satisfies achieves nothing.

One further omission is worth explaining, since a reader comparing this with the baseline will notice it. The baseline's encryption attribute is inherited and still required, so an interface states the bulk algorithm it uses. What this profile does not add is an encryptionSupported counterpart. Symmetric encryption at adequate key lengths is not the pressing concern in a post-quantum migration, and the interfaces needing work are identified by their key exchange and authentication. A profile combining migration with a broader agility objective would add it.

At the extended depth four more things stay out. Cipher suite lists are redundant with the decomposed attributes and cannot carry TLS 1.3 key exchange. Port numbers are deployment facts. Secret hygiene, such as how a database password is supplied, is not a migration fact. And individual keys are not identified, because how a key is identified across tools is still open (Q39): the profile describes the stores and what they can hold.

Expressing it in a CBOM

The attributes are format-independent. The full CycloneDX 1.7 mapping is in Formats.

  • Security protocols are protocol components. Each TLS interface is a cryptographic-asset with assetType: protocol. A TLS configuration shared by several interfaces is one further component, referenced from each.
  • Application protocols are services. OIDC, SAML, the Admin API and plain HTTP are CycloneDX services, and so is HTTPS. The dependency graph records what carries what: OIDC depends on HTTPS, HTTPS on the TLS component, and plain HTTP on nothing. A service is counted as an interface only when it carries interfaceType.
  • Native fields first. The implementing library is linked with dependencies[].provides. Supported TLS groups and signature schemes are in cipherSuites, which lists what is supported, while cryptoRefArray lists what is in use. Keys are related-crypto-material components, with securedBy stating how they are wrapped. Completeness is a composition.
  • Implementation facts are stated once, on the library that provides the interfaces, and inherited.
  • Everything else is a property under the pkic:profile: namespace: interface type, endpoint roles, the capability group and the key-management attributes, none of which CycloneDX models.
  • Links, not copies. The CBOM references its companion SBOM and the supplier's security advisories.

Where an attribute is unavailable, the four disclosure outcomes apply. none is a value, not a marker: it states that no algorithm is applied for that job, as with Keycloak's unencrypted tokens. A supplier that does not know whether an interface can coexist records coexistence as unknown instead of guessing, because a wrong answer produces a plan that fails at cutover.

Open questions for the working group

These are also carried in the open questions register, which collects the unresolved items from every section and maps each to the methodology aspect that tracks it.

  • Whether raising implementationPurl to a non-withholdable MUST is acceptable to vendors. It is the one place the baseline tightens the interface profile it extends.
  • Whether enablementMethod should be a single value or a set, since some capabilities need both an update and a configuration change.
  • Whether integrationConstraints can be structured usefully or should remain prose.
  • Whether an interface should be defined as a logical boundary rather than a port. Keycloak needs it, because its token signatures and its TLS migrate separately, but it means one port can carry several interfaces.
  • Whether implementation facts stated on a library and inherited by interfaces make a document harder to read than they make it shorter. Keycloak's document halves in size; a reader has to resolve the inheritance to see an interface's full answer.
  • Whether a CBOM should carry forward-looking data at all (Q26). This one is a substantive disagreement, not a detail to be tidied up. A procurement profile has a defensible claim on it; a runtime assurance profile arguably has none. Stating capability on library components as well as interfaces widens where the question applies.
  • How the family relates to a sector baseline. A telecommunications or finance profile would most likely add required interface types and constrain the acceptable algorithm sets, leaving the attribute list intact.
The pattern to take from this section: name the consumer and the decision, derive the questions that decision raises, and turn each question into an attribute that can be declared at the boundary. The list of attributes is the output of that analysis. Beginning instead from the fields a format happens to offer produces a profile with no stated purpose, and no way to argue about whether it asks for the right things.
