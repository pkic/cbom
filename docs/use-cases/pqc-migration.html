CHANGE PLANNING · WORKED USE CASE

PQC migration: from use case to profile

One use case is developed here, from the decision a consumer is trying to make through to two profile definitions. Both profiles are applied throughout to one real product: Keycloak 26.7.3, an open-source identity provider. The work follows the twelve steps set out in Method. It is the reference example for how the other use cases are worked up.

Illustrative. The profiles and example documents follow decision 0022, now published, which sets the migration profile (now v0.8), adds a second, more demanding profile (the extended depth, v0.1), and states how application-layer interfaces are expressed in CycloneDX. Both profiles extend the interface disclosure baseline v0.9, and the example documents are written in CycloneDX 2.0. Choices made provisionally in the consolidated baseline are listed in decision 0025. The attribute names are proposals made for this example, not established terms. The Keycloak values are taken from its documentation and issue tracker; the few still to be verified are marked.

The decision being supported

An operator or enterprise architect is evaluating a product it did not build and cannot inspect. It must decide how and when that product can move to post-quantum cryptography. An inventory says which algorithms are in use. The migration decision also depends on questions about integration, enforcement and planning, asked of every exposed interface:

  • Capability. Can this interface support post-quantum cryptography? Which algorithms can it negotiate for key exchange and authentication, and which protocol versions? These questions motivate protocolVersionsSupported, keyExchangeSupported and authenticationSupported, and the capability group G1, which states a status for each cryptographic purpose.
  • Enablement route. Is the capability already enabled, or does it need a configuration change, a software update, a licence or a hardware change? Which product version introduces it? These questions motivate enablementMethod, minimumProductVersion and providerLocation.
  • Operator enforcement. Can the operator require post-quantum algorithms and refuse a classical fallback? This question motivates negotiationControl. How the interface selects among algorithms, for example by a fixed list or a preference order, is not an attribute of either profile.
  • Integration friction. What will break when the capability is enabled? Typical causes are signature or ciphertext sizes, cookie and header limits, fragmentation and intermediaries. This question motivates integrationConstraints.
  • Blockers and roadmap. If an interface cannot yet do it, what is the obstacle, and who can remove it? Is a target release committed? These questions motivate capabilityStatus, blockedBy and roadmapRef.
  • Module validation. Is the implementing provider validated under a recognised scheme, such as FIPS 140-3 or ISO/IEC 19790? Can the post-quantum capability be used in validated mode? These questions motivate moduleValidationScheme, moduleValidationRef and validatedModeAvailability.
  • Key management and dependencies. Can the product's management surfaces create, hold and rotate the new key types? Are stored keys protected at rest? Which external services, such as certificate authorities, identity providers and directories, must migrate first? These questions motivate keyManagementFunction, keyOperations, keyTypesSupported, keyWrappingSupported, keyStoreRef and externalDependencies.

An inventory of algorithms cannot answer any of these questions. Knowing which algorithms an interface uses today leaves all of them unanswered. The questions concern what the interface is capable of, how that capability is enabled, and what enabling it costs in interoperability. A migration profile therefore has to require the facts those answers rest on.

For Keycloak the operator is typically an enterprise running it as the single sign-on service for its applications. Every relying party trusts the tokens Keycloak signs. Keycloak's migration therefore sets the timetable for many other systems as well as its own.

The black-box constraint

The defining constraint is that the consumer cannot see inside the product, and the vendor will not expose its internals. Everything the profile asks for therefore has to be declarable at the boundary: observable at an interface, or stated by the vendor as a property of the product it ships. Anything requiring disclosure of source, design or internal architecture is out of scope, and would not be supplied in any case.

The profile is also built around interfaces rather than around the product as a whole. A single answer at product level, such as "this product supports ML-KEM", does not tell the operator what to do. A product may support a post-quantum key exchange on its service interface and not on its management interface, and the operator has to migrate both. Migration is planned and executed one interface at a time.

The worked product: Keycloak 26.7.3

Keycloak is a useful subject because its most important cryptography is not TLS. It is the signature on every token it issues, which every relying party verifies. That signature migrates on a different timetable from the TLS underneath it, and depends on a different standard. A migration profile must be able to tell the token signature and the TLS apart. A profile that could not would fail on products like this one.

Three more properties make it instructive. Its TLS key exchange comes from the Java runtime rather than from Keycloak, so what blocks post-quantum key exchange lies with the runtime's cryptographic provider, not with Keycloak. It generates the key for its own cluster transport, so the product, not the operator, fixes that key's type. And it stores its realm keys in its database without wrapping (encrypting) them, so the key storage has to be treated as an interface too.

The subject is the container image, quay.io/keycloak/keycloak:26.7.3, at its defaults. The image fixes the Java runtime, and with it the TLS capability. The ZIP distribution runs on whatever runtime the operator installs, so its TLS capability is a fact about a deployment and belongs in a separate document.

This gives thirteen interfaces. The seven TLS interfaces all use the Java runtime's cryptographic providers. The four application-layer interfaces are implemented by Keycloak itself.

Two profiles, two depths

Keywords follow BCP 14. Both profiles are product-independent: no rule names a product, a vendor or an interface instance. Attribute names follow the conventions in Method: keyExchange and authentication denote what the interface uses now, and the Supported suffix denotes what it is able to use.

The questions split into two groups. The first is about the interface: what it does, what it could do, and what stands in the way. The second is about what surrounds the interface and has to move with it or before it: the surface that must create the new key, the store that must hold it, and the services it depends on. A supplier can usually answer the first group today. Many suppliers cannot yet answer the second. Putting both groups in one profile would set the minimum requirement so high that few suppliers could meet it. The use case is therefore served by a family of two profiles, ordered by depth: the extended profile asks for everything the baseline asks for, plus the second group of questions (decision 0019).

Group rule G1: capability, one entry per cryptographic purpose

Group rule G1 is keyed to the cryptographic purpose vocabulary. The vocabulary has seven values: key-establishment, encryption, entity-authentication, data-integrity, non-repudiation, key-protection and key-derivation. Its key coverage is all-purposes, so every interface carries an entry for all seven, not only for the three purposes the profile's scope takes in depth (C13). Each entry has the four members G1.1 to G1.4 listed above. Group members are evaluated inside each entry, so a conditional guard such as the one on blockedBy refers to that entry's own capabilityStatus. A guard may be removed (tightening) but never added or narrowed.

Conditional rules

Several rules apply only when another attribute has a particular value. A profile is not limited to a flat list of mandatory fields. A requirement can depend on the value of another attribute. I5 obliges a producer claiming that a capability needs a software update to say which version provides it. I11 asks for a certificate reference only where a validation scheme is declared, and I12 asks for wrapping algorithms only on a storage interface. Inside the capability group, G1.2 asks for a blocker only where a purpose is not available, and G1.4 asks about validated mode only where it is. Making these rules unconditional would not help. Requiring a version or a certificate from every interface produces noise. Requiring none leaves the useful case unstated.

Availability, and why it is not a date on an interface

An earlier draft of this profile put a plannedAvailability date on each interface. That is the obvious design, but it does not work, because of how interfaces gain capability.

Interfaces do not gain capability independently. A product with six TLS interfaces built on one cryptographic provider gains post-quantum key exchange on all six at the moment that provider is updated and the product integrates it. A date on each interface duplicates one underlying event six times, and the six copies drift apart as they are maintained. Availability is therefore a property of the change that delivers the capability, such as the provider update. The interfaces inherit it from that change.

What a planner needs first is therefore not the date but the obstacle, because the obstacle determines whether any date is credible and who is able to move it.

blockedByWhat has to happenWho can move itPredictability
providerA dependency is upgraded to a version offering the algorithm.The vendor, by taking the upgrade.Reasonable
productThe product's own code must change to expose or negotiate it.The vendor, in a named release.Reasonable
hardwareA module, firmware or platform must support the algorithm.The vendor together with the module supplier.Poor
standardNo specification yet defines the algorithm for this protocol.Nobody, until the standards process concludes.None
certificationA validated implementation is required, for example under a scheme such as FIPS.An external laboratory or scheme.Externally determined

The most important distinction is the fourth row, standard. An interface blocked on a protocol standard cannot be given a credible date by any vendor, and a consumer who understands that stops waiting and considers compensating controls instead. Recording it as "planned, date to follow" alongside a case that really is scheduled for the next release mixes up two situations that call for opposite responses.

Keycloak shows four of the five on one product. TLS key exchange is blocked by the provider: hybrid ML-KEM groups ship in JDK 27 and are enabled there by default, with backports to earlier releases announced, so the timing depends on the Java runtime's releases, not Keycloak's. Token signing is blocked by a standard: an ML-DSA signature provider is committed upstream, but the JSON Web Key representation it needs is still an Internet-Draft. The cluster transport is blocked by the product, because Keycloak generates its RSA-2048 key itself. And whether the capability will be usable in validated mode is a certification question for the Bouncy Castle FIPS module.

Where a date or release is offered, the profile keeps it out of the interface and out of the CBOM. Target release and date sit in a roadmap entry that interfaces reference through roadmapRef, so that interfaces sharing a blocker point at one entry. There are two reasons. First, a CBOM revision is a fixed record of one point in time. A date that slips either goes stale inside a document that looks authoritative, or forces the CBOM to be republished when nothing about the product has changed. Second, roadmap data has a different owner and changes at a different pace from the rest of the document. This is the same argument that the Governance section makes for keeping artifacts with separate lifecycles apart.

A target release is also preferable to a calendar date. Releases are the vendor's own unit of change, and the statement "this lands in 9.x" survives slippage in a way that a date does not.

Three existing parts of the methodology already support this approach, so nothing new has to be added. Forward-looking capability is carried by capabilityStatus, blockedBy and roadmapRef, not by the lifecycle stage. This profile accepts only implemented, and the interface disclosure baseline it extends no longer accepts intended at all. A migration plan cannot rest on cryptography that a producer has not yet implemented. The example cbom-keycloak-product-intended.cdx.json, a design record for Keycloak 27.0 with ML-DSA-65 token signing, fails baseline I8 on every interface for this reason. The same fact is already in the product record, as the status committed with a roadmap reference. The lifecycle stage says how the reported present state was obtained; the three attributes above say what is coming. A vendor that shares roadmap detail only under agreement records roadmapRef as withheld, meaning the information exists but is not disclosed. This is more informative than an empty field. And the freshness policy in Versioning applies to the roadmap entry, so a consumer can tell a current commitment from one nobody has revisited.

Capability, per purpose

Capability is stated per cryptographic purpose. Every interface carries one G1 entry for each of the seven purposes, and each entry has the members G1.1 to G1.4. The purposes of one interface migrate on different timetables, so they are answered separately. Across Keycloak, the two purposes that matter most look like this.

The other five purposes carry a status as well. On the TLS interfaces, encryption, data integrity and key derivation are available, and each says whether it works in validated mode. Key protection is not-planned everywhere. This repeats the storage finding: nothing wraps Keycloak's keys at rest. A deferred purpose owes only a status and, where it is not available, a blocker. That costs a producer almost nothing, and it keeps a shallower depth from becoming a permanent floor.

Most of these values are the same across interfaces because they are properties of the library that implements the interfaces. The document states them once, on that library, and an interface states only what differs. The cluster transport inherits the JDK's entries and overrides entity authentication. SAML inherits the Keycloak library's entries and overrides two purposes. Rules are evaluated on the values that result after inheritance and overrides.

A purpose is different from an operation. The purpose vocabulary is useful because it records that difference. CycloneDX already records operations: a certificate signature carries cryptoFunctions: ["sign", "verify"], and so would a firmware signature on the same product. The certificate signature serves entity authentication and migrates when the PKI does. The firmware signature must still verify years after it was written. The operation is the same, but the migration timescale and the work are different. See Terms for the four-part test an entry has to pass, and decision 0010 for the reasoning.

What a planner concludes

Without seeing inside the product, an operator reading the baseline document can conclude the following. No Keycloak interface can be made quantum-safe by configuration today. TLS key exchange arrives with the Java runtime, so the action is to track the runtime in the image and to test hybrid groups against the directory, the database and the mail server, which must support them too. Token signing will take the longest. It waits on a standard, so pressing the supplier for a date will achieve little. The time is better spent finding relying parties that reject unknown key types and flows that keep tokens in cookies. The cluster transport depends on a change in the product. Plain HTTP behind a proxy carries tokens in clear on the internal hop and should be closed first, because no post-quantum work protects traffic that is not encrypted at all. An inventory of the algorithms in use today yields none of these conclusions.

The extended document adds three conclusions to the baseline's. When ML-DSA signing lands, the key management surface must be able to generate the key as well, and today it cannot. Every baseline rule passes, and yet the operator could not migrate. pqc-migration-extended#I3 exists to catch this case. TLS migration cannot start until the operator's certificate authority can issue the new certificates, and the directory and identity providers have to follow. And the realm keys that sign every token sit unwrapped in the database, so a database backup is as sensitive as the signing service itself.

What the profiles deliberately exclude

The profile deliberately leaves out three kinds of information.

It carries no readiness or posture verdict. Whether a declared algorithm set counts as quantum-safe is a judgement against criteria still under revision, so an external policy computes it from these facts at the time of asking and dates the result. Policy Evaluation sets out the reasoning, which is also why pqcPosture was dropped from the baseline profile.

Maturity scores are excluded on the same grounds. Collapsing different attributes into one number has a further drawback. It tends to hide whichever attribute is actually blocking the migration.

Internal implementation is out of scope, so no source references, design detail or component structure are requested. This exclusion follows directly from the black-box constraint. It is not a compromise made to accommodate vendors. A vendor asked to expose internals will decline, and a profile nobody satisfies achieves nothing.

The profile also omits an encryptionSupported attribute. The encryption attribute from the interface disclosure baseline is inherited and still required, so an interface states the bulk algorithm it uses. What this profile does not add is an encryptionSupported counterpart. Symmetric encryption at adequate key lengths is not the pressing concern in a post-quantum migration, and the interfaces needing work are identified by their key exchange and authentication. A profile combining migration with a broader agility objective would add it.

The extended profile leaves out four more things. Cipher suite lists repeat what the separate key exchange, authentication and encryption attributes already state, and they cannot carry TLS 1.3 key exchange. Port numbers are deployment facts. Secret hygiene, such as how a database password is supplied, is not a migration fact. And individual keys are not identified, because how a key is identified across tools is still open (Q39): the profile describes the stores and what they can hold.

Expressing it in a CBOM

The attributes do not depend on any format. The example documents use CycloneDX 2.0, and the full mapping is in Formats. A CycloneDX 1.7 form of the product record, legacy/cbom-keycloak-product-1.7.cdx.json, carries the same facts and receives the same verdicts, flagged as legacy. The converter cdx17_to_20.py turns a 1.6 or 1.7 CBOM into 2.0.

  • Security protocols are protocol components. Each TLS interface is a cryptographic-asset with assetType: protocol. A TLS configuration shared by several interfaces is one further component, referenced from each.
  • The subject is the inventory's subject. CycloneDX 2.0 names the subject in inventories[0].subject; there is no metadata.component. Package URLs are identifiers[], each asserted by a named party.
  • Application protocols are services. OIDC, SAML, the Admin API and plain HTTP are components of type: "service", and so is HTTPS. The dependency graph records what carries what: OIDC depends on HTTPS, HTTPS on the TLS component, and plain HTTP on nothing. A service is counted as an interface only when it carries interfaceType.
  • Native CycloneDX fields are used first. The implementing library is linked with dependencies[].provides. Supported TLS groups and signature schemes are in cipherSuites, which lists what is supported, while relatedCryptographicAssets lists what is in use. Module validation and product certification go in the native certifications[]. Keys are related-crypto-material components, with securedBy stating how they are wrapped. Completeness is a composition.
  • Implementation facts are stated once, on the library that provides the interfaces, and inherited.
  • Everything else is a property under the pkic:profile: namespace: interface type, endpoint roles, the capability group and the key-management attributes, none of which CycloneDX models.
  • Related documents are linked, not copied. The CBOM points to its companion SBOM by BOM-Link and hash, to the supplier's security advisories and the OSV API, and to the security contact. It states that no VEX statements are published. Each pointer carries the property pkic:profile:context. See Context Pointers.

Recorded decisions

Several choices in these profiles were made against the more obvious alternative. Each is written up as a decision record in the repository, with the options considered, the rationale and what reversing it would involve. The records are authoritative. The summaries below are only for orientation.

RecordDecisionAspect
0002 Capability is stated as facts. The profile requires the algorithm sets an interface supports and does not ask whether they amount to being quantum-safe. That judgement is made by an external policy at the time of asking, for the reasons given in Policy Evaluation. 3.3
0007 Availability is expressed as a status and a blocker. Dates and target releases sit in a referenced roadmap entry, away from the interface. 3.10
0010 Capability is stated per cryptographic purpose. Capability status, blocker, roadmap reference and validated-mode availability are the four members of a purpose-keyed group rule (G1). An interface carries one entry for each of the seven purposes in the vocabulary, rather than one attribute per mechanism. 3.7
0019 Adoption is staged by a family of profiles ordered by depth. The baseline and extended profiles are two depths of one family. 3.9
0022 The two depths, and how they meet a real product. Module validation and storage in the baseline; key management and dependencies in the extended profile; an interface is a logical boundary; application protocols are CycloneDX services; native fields first; implementation facts inherited from the providing library. 3.9

The rules above also depend on decisions taken elsewhere in the methodology: 0004 for what this profile is permitted to change in the baseline it extends, and 0005 for the Supported suffix. The full index is in decisions/.

Open questions for the working group

These are also carried in the open questions register, which collects the unresolved items from every section and maps each to the methodology aspect that tracks it.

  • Whether raising implementationPurl to a non-withholdable MUST is acceptable to vendors. It is the one place where the baseline makes a rule of the interface profile it extends stricter.
  • Whether enablementMethod should be a single value or a set, since some capabilities need both an update and a configuration change.
  • Whether integrationConstraints can be structured usefully or should remain prose.
  • Whether an interface should be defined as a logical boundary rather than a port. Keycloak needs it, because its token signatures and its TLS migrate separately, but it means one port can carry several interfaces.
  • Whether implementation facts stated on a library and inherited by interfaces make a document harder to read than they make it shorter. Keycloak's document halves in size, but a reader has to resolve the inheritance to see an interface's full answer.
  • Whether a CBOM should carry forward-looking data at all (Q26). This one is a substantive disagreement, not a detail to be tidied up. A procurement profile has a defensible claim on it. A runtime assurance profile arguably has none. Stating capability on library components as well as interfaces widens where the question applies.
  • How the family relates to a sector baseline. A telecommunications or finance profile would most likely add required interface types and constrain the acceptable algorithm sets, leaving the attribute list intact.
The pattern to take from the PQC migration example: name the consumer and the decision, derive the questions that decision raises, and turn each question into an attribute that can be declared at the boundary. The list of attributes is the output of that analysis. Beginning instead from the fields a format happens to offer produces a profile with no stated purpose, and no way to argue about whether it asks for the right things.
