BACKGROUND

Challenges with SBOMs and current CBOMs

CBOMs inherit both the promise and the growing pains of software bills of materials, then add cryptography-specific problems on top. Understanding these is what motivates a profile-first, format-independent methodology.

What SBOM adoption taught us

Three properties have repeatedly separated smooth SBOM rollouts from painful ones, and each applies directly to CBOMs in a multi-vendor environment.

LessonThe problemImplication for CBOMs
HarmonizationA proliferation of vendor-specific formats and delivery methods made reconciliation impossible at scale.Converge on one machine-readable format (CycloneDX today) and consistent delivery across the supply chain.
ProfilingExhaustive coverage is not useful coverage — thousands of entries bury the ones a decision needs.Define a minimum, purpose-built subset of attributes per objective. This is the whole point of a profile.
NormalizationDifferent producers spell the same thing differently, breaking automation.Agree identifiers (syntactic) and attribute meanings (semantic) so tools can compare CBOMs at all.

CBOM-specific challenges

Beyond the SBOM inheritance, cryptography introduces its own difficulties that current standards only partly address.

1 · No first-class model for relationships (the edge gap)

Today's CBOM standards model cryptographic assets (algorithms, keys, certificates, protocols) as nodes, but have no object that represents the relationship — the place where cryptography is applied between two parties. A TLS connection is not an asset; it is a locus that uses assets. Classifiers that belong to the connection itself (endpoint roles, PQC posture of a specific session) end up pinned to a protocol asset, treating the edge as if it were a node.

2 · SPDX has no cryptographic object model yet

As of SPDX 3.0.1 there is no dedicated crypto model equivalent to CycloneDX's. Organizations standardizing on SPDX today typically pair it with a CycloneDX-format CBOM as a linked artifact. That works, but it means CBOM interoperability effectively depends on one format. See Formats.

3 · Inconsistent algorithm naming

Real deployments showed the same algorithm written many ways (AES256, AES-256-GCM, AES_256_CBC), which impeded policy enforcement and cross-organization analysis. CycloneDX 1.7's Cryptography Registry gives stable identifiers to close this — but older CBOMs still carry free text and must be normalized at ingest. See Versioning.

4 · Lifecycle and state ambiguity

"The product uses ML-KEM" can mean four very different things: it is intended in the design, implemented in the binary, configured in a deployment, or observed on the wire. A vendor's build-time CBOM and an operator's runtime scan legitimately disagree. Without an explicit lifecycle tag, consumers cannot tell capability from actuality. See Lifecycle Data.

5 · Depth versus disclosure

Over-reporting drowns the signal; under-reporting hides real risk and can also expose intellectual property. There is a genuine tension between operational utility and legitimate vendor confidentiality. A well-defined profile sets a floor that prevents underreporting while bounding what must be disclosed.

6 · Tooling coverage and confidence

Automated scanners can miss cryptography that is dynamically loaded, configuration-driven, or provided by hardware. A CBOM is only as trustworthy as the process that produced it, so provenance and, ideally, signing matter — and a CBOM's confidence varies by the lifecycle phase it was captured in.

7 · Linking crypto to its environment

Knowing a system uses ML-KEM is incomplete without knowing the library version that implements it (does it support hybrid mode?) and whether it runs in software, an HSM, or a TEE — the last potentially requiring a hardware refresh rather than a software update. CBOMs are therefore produced and consumed alongside SBOMs, and sometimes HBOMs. Cleanly linking the three is still maturing.

8 · Versioning and legacy artifacts

Standards move (CycloneDX 1.6 → 1.7), profiles tighten, and a product's CBOM is regenerated over time. Treating "old" as a single idea produces false verdicts; the three version axes must be handled deliberately. See Versioning.

Most of these reduce to two needs a profile methodology is designed to meet: bound what must be disclosed (profiling), and agree what the disclosed values mean (normalization + an explicit lifecycle and relationship model).
