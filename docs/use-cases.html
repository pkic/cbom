Where profiles could be used

A profile turns a CBOM from a document someone reads into a check a machine runs. Each use case below needs a different subset of attributes — which is exactly why profiles, not one universal schema, are the right unit. A single CBOM can satisfy several of these at once.

The use cases

1 · PQC migration readiness & planning

Goal: build evidence-based migration timelines and track progress toward quantum-safe. Profile shape: requires pqcPosture on every interface and often a specific lifecycleStage (compare implemented capability against observed actuality). Producer → consumer: vendor build / operator scan → migration planners and regulators. Example: compare current CBOMs against a quantum-safe target state to separate software-only updates from hardware refreshes.

2 · Procurement & tender conformance

Goal: state cryptographic requirements in a tender and check a vendor's CBOM against them automatically, replacing bespoke security questionnaires. Profile shape: per-interface minimums plus product-level structure (e.g. "declare a management interface"). Producer → consumer: vendor → operator procurement. Example: a required baseline for any product terminating an operator interface.

3 · Vulnerability management & incident response

Goal: when a library flaw lands (say an OpenSSL CVE), find every affected service fast. Profile shape: makes implementationPurl mandatory so CBOMs cross-reference cleanly against vulnerability feeds. Producer → consumer: build pipeline → security operations. Example: query the CBOM repository for all interfaces implemented by pkg:generic/openssl@<affected>.

4 · Regulatory & compliance reporting

Goal: demonstrate posture against frameworks such as the EU CRA, NIS2, BSI TR-03183 / TR-02102, or US directives. Profile shape: encodes the specific attributes a regulation expects into a checkable rule set; conformance becomes an artifact. Producer → consumer: operator → auditor / regulator. Example: a jurisdiction-specific profile a global vendor can satisfy once and report many times.

5 · CI/CD quality gate

Goal: stop non-conforming crypto from reaching production. Profile shape: any profile, run as a pipeline step that fails the build on a MUST violation. Producer → consumer: build → the pipeline itself. Example: exactly the pass/fail behaviour on the Demo page, wired into CI.

6 · Crypto-agility assessment

Goal: judge how quickly an estate could swap an algorithm out. Profile shape: emphasises implementationPurl, keyExchange/encryption/authentication separation, and dependency links, so agility can be reasoned about per interface. Producer → consumer: vendor → architecture / risk. Example: flag interfaces whose crypto is hard-wired rather than provider-swappable.

7 · Supply-chain transparency

Goal: give downstream consumers a consistent, high-fidelity disclosure instead of free-form documentation. Profile shape: a disclosure baseline (like this example) that bounds what must be shared while protecting IP. Producer → consumer: tier-N supplier → integrator. Example: one vendor CBOM satisfies many operators' baselines.

8 · Mergers & third-party risk due diligence

Goal: assess an acquisition target's or partner's cryptographic exposure quickly. Profile shape: a broad disclosure + PQC-posture profile applied across their estate. Producer → consumer: target → acquiring security team. Example: surface deprecated algorithms and legacy-hardware-bound crypto before signing.

Which attributes each use case leans on

The same twelve attributes serve all of these, but each use case makes a different subset mandatory — the essence of profiling.

One CBOM, many profiles. A vendor generates a single high-fidelity CBOM; different consumers run it against the procurement, PQC-readiness, and vulnerability profiles independently. That is the payoff of keeping the methodology format-independent and the requirements in profiles.
