Use cases for profiles

A profile enables a CBOM to be evaluated automatically rather than assessed manually. Each use case below requires a different subset of attributes, which is the reason profiles, rather than a single universal schema, are the appropriate unit. A single CBOM may satisfy several of these use cases simultaneously.

Use cases

1 · PQC migration readiness and planning

Objective: establish evidence-based migration timelines and track progress toward quantum-safe cryptography. Profile emphasis: requires disclosure of the key-exchange and authentication algorithms — the facts from which post-quantum posture is derived by an external policy (see Policy Evaluation) — and frequently a specific lifecycleStage, so that implemented capability can be compared with observed actuality. Producer and consumer: vendor build or operator scan, consumed by migration planners and regulators. Example: comparison of current CBOMs against a quantum-safe target state to distinguish software-only updates from changes requiring hardware replacement.

2 · Procurement and tender conformance

Objective: state cryptographic requirements in a tender and evaluate a vendor's CBOM against them automatically, in place of security questionnaires. Profile emphasis: per-interface minimums together with product-level structure, such as the requirement to declare a management interface. Producer and consumer: vendor, consumed by operator procurement. Example: a required baseline for any product that terminates an operator interface.

3 · Vulnerability management and incident response

Objective: when a library vulnerability is disclosed, such as an OpenSSL advisory, identify every affected service promptly. Profile emphasis: requires implementationPurl so that CBOMs can be cross-referenced against vulnerability feeds. Producer and consumer: build pipeline, consumed by security operations. Example: a query of the CBOM repository for all interfaces implemented by pkg:generic/openssl@<affected>.

4 · Regulatory and compliance reporting

Objective: demonstrate cryptographic posture against frameworks such as the EU CRA, NIS2, BSI TR-03183 and TR-02102, or United States directives. Profile emphasis: encodes the attributes a regulation expects into a checkable rule set, so that conformance becomes a defined artifact. Producer and consumer: operator, consumed by auditors and regulators. Example: a jurisdiction-specific profile that a global vendor satisfies once and reports against in multiple jurisdictions.

5 · Continuous integration quality gate

Objective: prevent non-conforming cryptography from reaching production. Profile emphasis: any profile, executed as a pipeline stage that fails the build on a MUST violation. Producer and consumer: the build, consumed by the pipeline. Example: the pass and fail behaviour shown on the Demo page, integrated into continuous integration.

6 · Crypto-agility assessment

Objective: assess how readily an estate could replace an algorithm. Profile emphasis: emphasises implementationPurl, the separation of keyExchange, encryption, and authentication, and dependency links, so that agility can be assessed per interface. Producer and consumer: vendor, consumed by architecture and risk functions. Example: identification of interfaces whose cryptography is fixed rather than provider-replaceable.

7 · Supply-chain transparency

Objective: provide downstream consumers with a consistent, high-fidelity disclosure in place of free-form documentation. Profile emphasis: a disclosure baseline, such as this example, that bounds the information to be shared while protecting intellectual property. Producer and consumer: a supplier at any tier, consumed by an integrator. Example: a single vendor CBOM that satisfies the baselines of multiple operators.

8 · Mergers and third-party risk due diligence

Objective: assess the cryptographic exposure of an acquisition target or partner. Profile emphasis: a broad disclosure and PQC-posture profile applied across the estate. Producer and consumer: the target, consumed by the acquiring security function. Example: identification of deprecated algorithms and cryptography bound to legacy hardware prior to completion.

Attributes emphasised by each use case

The same set of attributes serves all of these use cases, but each makes a different subset mandatory. This selectivity is the defining characteristic of profiling.

A single CBOM may satisfy multiple profiles. A vendor generates one high-fidelity CBOM, and different consumers evaluate it independently against the procurement, PQC-readiness, and vulnerability profiles. This is a direct consequence of keeping the methodology format-independent and locating the requirements in profiles.
