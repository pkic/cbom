CONCEPT

Context pointers

A CBOM records cryptographic facts about one subject at one stage. A consumer usually needs more than those facts: the SBOM of the same product, the vendor's vulnerability statements, the configuration a deployment record was read from, the evidence behind an observation. These artefacts change on their own schedule, or another party holds them. A CBOM therefore does not carry them. It points to them. A profile states which pointers a document must contain, and the validator checks them.

The construct

A profile declares two things: the kinds of context it knows about, and the rules that require a pointer to one of them. The rules form a separate kind of rule, with the letter R, beside product rules (P) and interface rules (I). They are cited like any other rule, for example interface-disclosure#R2.

Context kinds

The profile's contextKinds block defines each kind. For each kind, it names the CycloneDX externalReferences types that can carry it, and its form:

  • document: a fixed artefact. The pointer binds it by a hash, so a consumer can tell whether the artefact has changed.
  • endpoint: a feed, an API or a web page whose content changes over time. The pointer names its access protocol, so a consumer knows how to read it.
  • document-or-endpoint: either of the two, as the producer chooses.

Reference rules

A reference rule names the kind it requires and sets these fields:

FieldWhat it says
contextThe context kind the pointer must have.
atWhere the pointer sits: on the document (the subject) or on each interface.
levelMUST, SHOULD or MAY.
hashRequiredWhether the pointer must carry a hash of the target. The value when-document requires a hash only when the target is a document.
withholdableWhether the producer may withhold the pointer. See Confidentiality.
orDeclaredAbsentWhether the producer may state instead that no such artefact exists, with a value from contextAbsenceVocabulary: not-published or not-applicable-to-subject.
requiredWhenThe condition under which the rule applies, such as a subject type, a document stage, or an attribute value.

The baseline's rule R2 shows the fields together:

{
  "id": "R2",
  "context": "vulnerability-statements",
  "at": "document",
  "level": "MUST",
  "hashRequired": "when-document",
  "orDeclaredAbsent": "contextAbsenceVocabulary",
  "withholdable": false,
  "requiredWhen": { "subjectType": "product" }
}

The profile checker tests every profile against check C18. Every reference rule must name a context kind that the profile family defines, and that kind must be carried by real CycloneDX reference types. A profile cannot require a pointer that no document can express.

Two principles

Conformance checks the pointer, never the target

The validator checks that the pointer is present and well formed. It checks that a document pointer carries a hash where the rule requires one, and that an endpoint pointer names its access protocol. Where the evaluator receives the target itself, as with a cited document passed with --with, it checks that the hash matches. It never evaluates the target's content. A Keycloak product record that points to the OSV API passes rule R3 whether or not OSV holds any advisory for Keycloak. A deployment record that points to a data register passes rule R3 of the Deployment Disclosure profile without anyone reading the register.

This is decision 0020 generalised by decision 0025. A CBOM records facts that change when the product or the deployment changes. Context that changes on another trigger, or that another party holds, is joined and not merged.

Direction follows time

A record points to two kinds of target. The first kind exists when the producer writes the record: the companion SBOM, the configuration revision the record was read from, the evidence it was built on. The second kind is a place where later statements will appear: a VEX feed, an advisory API. The record can name that place in advance, because the place exists even though the statements do not yet.

Judgements made afterwards point the other way. A conformance claim and a policy result point to the record by its SHA-256 digest. A record never points to them. If it did, every new judgement would require a new revision of the record, and the record would stop being a stable statement of fact. Policy Evaluation describes the result format.

Three kinds of reference

A CBOM uses three kinds of reference. Only the third is a context pointer.

InternalAnother object in the same documentA bom-refkeyStoreRef, which names another object in the same record by its bom-ref
Cross-documentAnother CBOM or SBOM, or one object in itA BOM-Link (urn:cdx:<serial>/<version>, optionally #<bom-ref>) and a SHA-256 hashcorrespondsTo, cited documents, the companion SBOM

A BOM-Link is the CycloneDX way to name one revision of another BOM, and one object inside it. Two references look like pointers and are not. The PQC migration profile's per-purpose roadmapRef (group rule G1) stays a group attribute that holds a URL. Module validation and product certification are native certifications[] in CycloneDX 2.0, so they need no pointer.

How a pointer is carried in CycloneDX

A pointer is an entry in externalReferences. A document-level pointer sits on the subject. An interface-level pointer, such as configuration guidance or observation evidence, sits on the interface's component. Each entry carries four things:

  • a CycloneDX reference type, from the carrier types of its kind;
  • the property pkic:profile:context, which names the kind. The property is needed because kinds share types: documentation alone can carry configuration guidance, design intent, an issuer policy or a support lifecycle;
  • for an endpoint, the property pkic:profile:accessProtocol, from web-page, csaf-provider, osv-api, ghsa-api, vex-document or other;
  • for a document, a hashes entry with a SHA-256 value.

CycloneDX 2.0 allows properties on external references, which makes the two properties possible. Two pointers from the Keycloak product record show both forms:

"externalReferences": [
  {
    "type": "bom",
    "url": "urn:cdx:6b3c1d2e-7a41-4c1e-9f0a-26730000b000/1",
    "properties": [ { "name": "pkic:profile:context", "value": "sbom" } ],
    "hashes": [ { "alg": "SHA-256", "content": "11234911bf74…" } ]
  },
  {
    "type": "advisories",
    "url": "https://api.osv.dev/v1/query",
    "properties": [
      { "name": "pkic:profile:context",        "value": "advisories" },
      { "name": "pkic:profile:accessProtocol", "value": "osv-api" }
    ]
  }
]

A stated absence is a property on the subject, named after the kind. The Keycloak product record carries pkic:profile:contextAbsent:vulnerability-statements with the value not-published, and the same for support-lifecycle.

What is deliberately not pointed to

  • Judgements made after the record. A record does not point to a conformance claim or a policy result about itself. Those point to the record by digest.
  • The vulnerability data itself. The record points to where advisories and VEX statements are published. It carries none of them. Vulnerabilities follows the join from the record to the advisories.
  • Facts that have a native field. Module validation and product certification are certifications[] in CycloneDX 2.0. Key rotation and renewal are native too. A pointer would duplicate them.
  • Planning information per purpose. The PQC migration profile keeps roadmapRef as a group attribute beside the capability status it explains, such as Keycloak's ML-DSA token signing, committed, with roadmap issue #43690.
  • The content of any target. No rule checks what a target says. A consumer who relies on a target reads it and judges it separately.
In short. A context pointer names an artefact that a CBOM needs and does not carry. A profile defines the kinds of context, the reference types that carry each kind, and whether the target is a document bound by a hash or an endpoint with an access protocol. Reference rules say which pointers a document must contain. Conformance checks the pointer and never the target. A record points to what exists when it is written and to the places where later statements will appear. Judgements made afterwards point to the record by digest.
