The profile: Interface Disclosure Baseline

This profile is product-independent. It states structural requirements — which categories of interface must exist, and what each must disclose — and therefore applies to any product. It does not reference a specific product or interface instance.

A profile must not bind a rule to a specific product or interface. An earlier draft incorrectly required interfaceId to equal "nginx-https". Rules instead constrain the set of interfaces and the attributes of each interface.

Two directions of use

A single attribute table is applied in two directions.

Two rule groups

Product-level rules (constraints on the set of interfaces)

#RequirementLevelConstraint
P1Declare at least one cryptographic interfaceMUSTminInterfaces: 1
P2Declare at least one management interfaceMUSTminInterfacesOfType: {management, 1}

Per-interface rules (applied to every interface)

Names follow the conventions in Method. The bare name denotes present state, so keyExchange is what the interface uses; a profile needing declared capability adds the Supported suffix, as the PQC Migration profile does.

#AttributeLevelNotes
I1protocolMUSTTLS, SSH, IPsec, and similar
I2protocolVersionMUST
I3keyExchangeMUSTregistry algorithm identifier
I4encryptionMUSTbulk or AEAD algorithm
I5authenticationMUSTcertificate signature (TLS) or host key (SSH)
I6endpointRolesMUSTat least two endpoints
I7interfaceTypeMUSTfrom the controlled vocabulary
I8lifecycleStageMUSTsee Lifecycle Data
I9implementationPurlMUSTPackage URL of the implementing library. Withholdable: a withheld marker satisfies the rule, silent omission does not. This is the one rule here where the disclosure model decides the verdict.
A CBOM conforms if and only if the carrier format is accepted, every product-level MUST rule holds, and every declared interface satisfies every per-interface MUST rule. interfaceId is an instance label chosen by the producer and is not constrained by the profile. The full statement of what conformance means, including what a passing verdict does not assert, is in Conformance.

Derived evaluations such as post-quantum posture are deliberately not profile attributes. They are computed by an external policy from the disclosed facts, because the criteria on which they depend change over time. See Policy Evaluation.

Disclosure states

An attribute with no value may be missing for different reasons, and the profile distinguishes them. Following the 2026 SBOM minimum elements, a producer states whether the information is unknown to it or is being withheld.

OutcomeMeaningEffect on a MUST rule
valueA value was supplied and checked against the constraint.Passes if valid.
withheldThe producer holds the information and declines to publish it.Passes only where the rule is marked withholdable.
unknownThe producer does not have the information.Fails, but is reported as unknown rather than absent.
undeclaredNeither a value nor a marker was supplied.Fails.

An unknown value does not satisfy a MUST rule, because the requirement has not been met. It is still reported separately from an undeclared one: the first records a limit of the producing process, the second records that the question was not addressed. In this profile only I9 is withholdable, on the basis that a producer may decline to publish a library version while still meeting the disclosure objective. A procurement profile might permit no withholding at all. See Challenges and Demo.

Composition: how profiles relate to each other

Two different things are meant when profiles are combined, and keeping them apart matters because they carry different guarantees.

Independent evaluation

A CBOM may be evaluated against any number of profiles, each producing its own verdict. The profiles need not know of each other and are not combined. This is what the claim that one document serves several purposes amounts to: a vendor publishes once, and a procurement team, a migration planner and a vulnerability responder each apply the profile matching their decision.

Two conditions make this work. Attribute names are global across the methodology, so a name means the same thing in every profile that uses it, which is why the naming conventions and the attribute table in Terms apply to all profiles and not to each in isolation. And a verdict is always reported per profile; conformance to one says nothing about another.

Extension

A profile may declare that it extends another. It then inherits every rule of the base and states only what it adds or changes. A sector baseline built on a general one, and the PQC migration profile built on the interface disclosure baseline, are both of this kind.

Extension is monotonic: a derived profile may add rules and tighten inherited ones, and may not relax them. The consequence is the property that makes extension worth having, which is that a document conforming to the derived profile also conforms to the base. Without it, a claim of conformance to a sector profile "based on" the baseline would tell a consumer nothing about the baseline, and the word "based" would be doing misleading work.

Operation on an inherited rulePermittedWhy
Raise the level, SHOULD to MUSTyesTightening. Anything satisfying the derived rule satisfies the base rule.
Narrow a constraint, such as restricting an enumeration to a subset or raising a minimum countyesTightening.
Make a withholdable attribute non-withholdableyesTightening.

A profile that genuinely needs to relax a base requirement is not an extension of it. It is an independent profile, and should be written and claimed as one. Treating that as a restriction rather than an inconvenience keeps conformance claims meaningful.

Pinning, ranges and identifiers

  • The base version is pinned. A derived profile names the base profile and the exact version it extends. A later release of the base has no effect until the derived profile's author re-pins and re-checks, which follows the general treatment of profile versions in Versioning.
  • The carrier acceptance range may narrow, never widen. A derived profile cannot accept a format version the base excludes, since the base's adapter may be unable to read it.
  • Inherited rules keep the base's identifiers. A report can then say that I3 comes from the baseline and M9 was added by the derived profile, and a reader can trace any failure to the profile that imposed it.
  • Single inheritance only, for now. A profile extends at most one base. Multiple inheritance raises conflicts between bases that would need resolution rules, and no case requiring it has arisen.

Expressing a conformance claim

A claim names every profile evaluated, each with its version, together with the carrier format version and the content revision. For a derived profile the base is named as well, because the derived profile pins a particular version of it and a reader should not have to look that up.

Conforms to:
  pkic.example.pqc-migration v0.1
    extending pkic.example.interface-disclosure v0.3
  pkic.example.interface-disclosure v0.3   (independently evaluated)
Carrier: CycloneDX 1.7
Content revision: 3

Machine-readable form

A derived rules file declares its base and lists only its additions and its tightenings.

{
  "profileId": "pkic.example.pqc-migration",
  "version": "0.1",
  "extends": { "profileId": "pkic.example.interface-disclosure", "version": "0.3" },
  "overrides": [
    { "id": "I9", "level": "MUST", "withholdable": false }
  ],
  "interfaceRules": [ ... rules added by this profile ... ]
}

A validator loading such a file resolves the base, applies the overrides, and rejects any override that relaxes an inherited rule. That check is worth implementing early, because a relaxing override is easy to write by accident and its effect on a conformance claim is not obvious from reading the file.

Conformance pipeline

The validator applies four stages in sequence. The content stages are evaluated only if the format stage accepts the CBOM.
