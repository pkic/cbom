MAPPING

One profile against two formats

A PKIC CBOM profile is defined independently of any format. A mapping locates each attribute, and the interface count, within a concrete document. The target carrier is CycloneDX 2.0. The validator still reads CycloneDX 1.6 and 1.7 documents, as legacy, because the tools that produce CBOMs today emit 1.x. SPDX 3.0.1 has no cryptographic object model, so a CBOM is expressed in CycloneDX and referenced from an SPDX SBOM. SPDX 3 is not a target carrier, and the SPDX column of the mapping keeps its stated gaps.

Both formats permit the same information to be encoded in more than one valid way. The mapping therefore also normalizes the encoding. It defines a single, canonical location for each attribute. A consumer that relies on the mapping reads each required value from one place. It does not have to handle every valid variant, and this reduces parsing complexity. See Challenges.

CycloneDX 2.0 is not yet released. The PKIC CBOM profiles are pinned to the development branch 2.0-dev of CycloneDX/specification, commit 76f185c (23 October 2026). Ecma is expected to ratify the release in December 2026. When it does, the working group replaces the pinned schema, regenerates the examples and revises any location that moved. When a format gains capability, the mapping changes and the profile rules do not. This is the practical benefit of keeping the profile separate from any format.

The target carrier: CycloneDX 2.0

Every published example is a CycloneDX 2.0 document, except the two under examples/legacy/. The repository holds the pinned 2.0 schema in tests/schemas/cyclonedx-2.0/, and the test suite validates every 2.0 example and perspective against it. Every profile declares the carrier range "cyclonedx": { "min": "1.6", "tested": "2.0" }. See Versioning.

CycloneDX 2.0 changes where several facts sit. The profile attributes do not change. The changes that matter to the PKIC CBOM profiles are these:

CycloneDX 2.0 also adds a root risks array: a risk register with status, owner, responses and target dates. These values are judgements, not product facts. The validator ignores risks for conformance, and a supplier's product record should not contain them (decisions 0002 and 0007).

Reading CycloneDX 1.6 and 1.7

The validator reads both carrier generations. For a 1.x document it takes the subject from metadata.component, the services from services[], and the in-use algorithms from cryptoRefArray and algorithmRef. For a 2.0 document it takes the same facts from their 2.0 locations. Both readings produce the same abstract record, so every rule is written once. The report places a 1.6 or 1.7 document in the legacy band and says so. The verdicts do not change. examples/legacy/cbom-keycloak-product-1.7.cdx.json holds the same facts as the Keycloak 2.0 product record, and it receives the same verdicts against all five product profiles.

A producer can convert a 1.6 or 1.7 CBOM to 2.0 with cdx17_to_20.py. The converter re-encodes existing facts and adds none. It moves the subject into inventories[0].subject, turns each service into a component of type service, moves package URLs into identifiers[] asserted by the document author, and replaces cryptoRefArray and algorithmRef with relatedCryptographicAssets. It also turns the 1.x property pkic:profile:subjectIdentifier into an identifier with the custom scheme tag-uri, and a library's module validation into a certifications[] entry. Its docstring lists every conversion. It targets the pinned commit and will need revisiting when 2.0 is released.

Two locations, two meanings

A concrete case shows why the mapping names one location for each fact. Take one interface from the worked example: TLS on Keycloak's main listener, port 8443. The JDK 21 in the image offers several key-exchange groups, with X25519 first, and X25519 is what the interface uses by default. CycloneDX can record X25519 in two places for the same interface, and both are valid. In the published example the cipher suites sit in a shared TLS configuration component that the interface references. The figure shows them inline for brevity.

Neither location is wrong, and the Keycloak example uses both. The mapping gives each one a single meaning. cipherSuites lists the supported set. The validator reads its tlsGroups and tlsSignatureSchemes as the supported key-exchange groups and signature schemes, which the pqc-migration profile requires. relatedCryptographicAssets lists what the interface uses. Only entries that point to algorithm components count as in use. A TLS configuration that several interfaces share is one protocol component with the suites, and each interface references it with type: "protocol-configuration". The validator follows that reference for the supported set and does not treat it as in use.

The same pattern appears for authentication. A TLS interface usually reaches its signature algorithm through a certificate component. In 2.0 that link is the certificate's relatedCryptographicAssets. In 1.x it is certificateProperties.signatureAlgorithmRef. An SSH interface has no certificate, so the interface references the host key algorithm directly. Both forms satisfy the profile requirement for an authentication algorithm, and the mapping records which form applies in which case. At the implemented stage, Keycloak's server certificate is supplied by the operator, so the product record states authentication as deployment-defined and points to the guide where the operator sets it.

The mapping therefore does more than locate attributes. It also prevents a type of error in which a CBOM is complete but a consumer reports it as deficient, or reports an offered algorithm as one in use. Both errors arise only because the producer chose a different valid structure.

Representation of a cryptographic interface

A cryptographic interface, meaning a cryptographic relationship, is represented in one of two ways. A security protocol instance such as TLS is a cryptographic-asset component with assetType: protocol. An application protocol such as OIDC, SAML, the Keycloak Admin API or plain HTTP is a service. In CycloneDX 2.0 a service is a component with type: "service". The dependency graph carries the layering: OIDC depends on HTTPS, and HTTPS depends on TLS.

The profile's model and the format's model do not align at this point. The format treats a protocol as an asset, in the same category as an algorithm or a certificate. The profile treats the interface as a relationship between endpoints. The mapping bridges the two models. It uses the protocol component or service as the carrier for the relationship, meaning the object that holds the relationship's attributes. Those attributes are attached as pkic:profile: properties. SPDX 3.0.1 has no such carrier. For that reason the SPDX column reaches the same attributes through a linked CycloneDX document rather than natively. In both formats, attaching relationship attributes to the carrier is a convention agreed in the mapping. Neither format enforces it as a structure.

This arrangement has several consequences for an implementation:

  • The document does not declare the set of interfaces directly. The validator derives the set by listing the components that carry interfaceType, and counts them. Rules P1 and P2 are evaluated against that derived set, including the count of components with interfaceType = management.
  • Nothing in the format prevents a protocol component or service from being used for something other than an interface. A producer may declare a service only for its layering, such as HTTPS under OIDC. The interfaceType property distinguishes an interface from such a record. For this reason the profile requires interfaceType on every interface.
  • An interface is identified by its bom-ref. References inside the document, such as keyStoreRef, use it. A reference from another document uses a BOM-Link, urn:cdx:<serial>/<version>#<bom-ref>.
  • The algorithms belonging to an interface are reached by reference, rather than being contained within it. If a reference is broken or missing, the attribute appears to be absent.
  • A product and an operator each describe the same connection in their own records. The deployment record names the product interface it realises with pkic:profile:correspondsTo, and the records are joined, not merged. See Inventory.

A format may later introduce a dedicated object for the relationship. If it does, this part of the mapping changes and the profile's requirements do not.

The SPDX entries for the document-level rules and the interface classifiers are unresolved: P1 to P6, I6, I7, I8, I11, G1 and interface identity. I1 to I5 reach their values via a linked CycloneDX CBOM, which means the SPDX document references one external artifact. The SPDX document therefore contains one element for the linked CBOM, not one element per interface. As a result, SPDX has no element to which a per-interface annotation could be attached, and no set of elements that could be counted. Decision 0016 keeps these rows unresolved deliberately, and a conformance claim on an SPDX carrier states that document-level rules were not evaluable. The joins and the context pointers are not mapped to SPDX, because SPDX 3 is not a target carrier. The options, and the contributor expertise needed to choose between them, are set out in the mapping document and recorded as Q48.

Perspectives: informative companions

CycloneDX 2.0 adds perspectives. A perspective names a domain and lists JSONPath expressions into a document, each marked required, recommended or optional. Generic 2.0 tools can use a perspective to filter a document and check that expected fields are present, without the PKIC validator.

Each PKIC CBOM profile publishes one perspective, generated from its rules file by tools/build_perspectives.py, in perspectives/perspective-<profile>.cdx.json. A perspective cannot express conditions, vocabularies, groups, withholding, reference rules or extension. It is therefore informative only. The rules file is normative, and a document that satisfies a perspective may still fail the profile.

Two words that collide

CycloneDX 2.0 uses two of the methodology's words for its own concepts. Its root profiles element holds reusable data and threat characterisations. Its blueprint model defines an interface with types such as rest and cli. Neither is the concept used here. Wherever confusion is possible, the documentation writes "PKIC CBOM profile" for a rules file of this methodology, and "cryptographic interface" for a cryptographic boundary that a profile counts and describes (decision 0021).

Interpretation of the columns

In CycloneDX, the cryptographic assets (I1 to I5, I10 and the provider in I9) are represented in native fields. This is an area where the format is strong. CycloneDX 2.0 adds native homes for module validation and product certification, and the document stage sits in the native metadata.lifecycles. The profile also depends on interface-level classifiers: interfaceType (I7) and endpoint roles (I6), and on the subject type (P5). These have no native field. They are carried as properties under the pkic:profile: namespace. Rule P2 can only be evaluated because the interfaceType attribute is present.

In SPDX, version 3.0.1 has no cryptographic model, so most detail comes through the linked CycloneDX CBOM. SPDX is strong on provider identity (I9). It identifies the implementing library by packageUrl. A consumer cross-references that value against vulnerability feeds, as described in Vulnerabilities. As SPDX gains a cryptographic object model, entries in its column will move from the linked CBOM to native SPDX fields. The requirement numbers will stay the same. Stable requirement numbers are the reason for expressing the profile independently of the format.

The edge gap

interfaceType and endpoint roles describe the interface itself. In the relationship model, the interface is an edge: the connection between two endpoints. Neither format provides an object that represents the interface. Both formats attach these attributes to a node instead: the protocol component or the service. This is sufficient for the disclosure baseline. However, it cannot record a finding that belongs to the connection itself. One example is whether a particular session negotiated a key-exchange group that is not post-quantum. CycloneDX 2.0 does not close the gap. Its blueprint flows have a source and a destination, but they describe a deployed system for threat analysis, and their encryption flag is a boolean. The working group's first-class attributed-edge model aims to provide an object for the connection that can carry such findings.

Normalization

Normalization covers two separate questions: where a value is written in the document, and how the value itself is expressed. Both questions have to be settled before CBOMs from different producers can be compared. The second question, how the value is expressed, causes more difficulty in practice.

The mapping normalizes identity as well as encoding. Naming a canonical location settles where a value is read. It does not establish whether two documents that carry the value describe the same component, certificate, key, or interface. Where an identifier scheme exists the mapping can require it. Requirement P3 does so for the subject, I9 does so for the implementing library, and the registry does so for algorithms. Where no scheme exists, a mapping cannot supply an identity the formats do not define. Across documents, the deployment record supplies the link itself: correspondsTo names the product interface by BOM-Link. Identity normalization is still the harder of the two questions. The remaining work of matching records that describe the same asset is done in the inventory. See Challenges.

Why it matters

Every automated use of a CBOM depends on matching a value against something, whether a policy, a deprecation list, a vulnerability feed, or the same attribute in another CBOM. Those matches are exact. A value that means the right thing but is written differently will not match, and nothing in the process reports an error. A policy engine looking for AES-256-GCM that encounters AES256 finds no match. Depending on how the rule is written, it treats the interface either as compliant or as having no encryption at all. Both results are incorrect, and both look like ordinary output.

The problem grows with the size of the estate. A single supplier using an unusual spelling can be handled by hand. The same variance across many suppliers and a large number of interfaces makes estate-wide questions impractical to answer, such as how many interfaces still use a deprecated algorithm, or which services an advisory affects. Inconsistent naming seen in real deployments is the reason the registry was introduced.

What the registry solves

CycloneDX 1.7 introduced the Cryptography Registry, which assigns stable identifiers to algorithm families and their parameters. Elliptic curve names show the problem clearly. The same curve is commonly written three ways, depending on which standards body or library the producer follows:

As written by the producerOriginRefers to
P-256NISTThe same curve. The three strings have no form in common, so a text comparison treats them as unrelated.
secp256r1SECG
prime256v1ANSI, used by OpenSSL

Compared as text, these are three distinct values. Compared as registry identifiers, they are one value. CycloneDX 2.0 goes a step further for curves: ellipticCurve takes an enumerated value, such as nist/P-256 or other/Curve25519, in place of the free-text curve. Symmetric algorithms raise a related difficulty: AES256, AES-256-GCM, and AES_256_GCM may or may not denote the same thing, because the first omits the mode that the others state. The registry also separates the algorithm from its parameters, so a query for deprecated key sizes does not depend on parsing a name.

For requirements I3, I4, and I5 a registry identifier is preferred wherever one exists. CBOMs written to version 1.6 carry free-text names. The working group recommends that an adapter normalize these names with a versioned name map, so that rules only ever see canonical values. See Versioning.

Protocols need normalizing too

Algorithm naming receives most of the attention, but protocol identity presents the same difficulty. The protocol and its version are recorded as free text in protocolProperties and in service properties, and producers write them inconsistently: TLS, tls, and TLSv1.3; a version given as 1.3, TLS 1.3, or 0x0304; SSH as 2.0 or SSH-2.0. Some protocols have more than one accepted name, such as MACsec and IEEE 802.1AE.

There are several practical reasons to normalize protocol names and versions.

  • Profiles gate on protocol version. A rule requiring TLS 1.2 or higher has to compare versions, and comparison needs a defined ordering. Strings do not provide one: 1.10 sorts before 1.9 as text, and TLSv1.3 does not parse as a number at all.
  • Deprecation is expressed per protocol version. Guidance withdraws TLS 1.0 and 1.1, not TLS generally, so a policy cannot be applied unless the version is canonical.
  • The protocol determines which algorithm roles exist. TLS authenticates with a certificate signature, SSH with a host key, IPsec through IKE negotiation. A consumer that misreads the protocol looks for the wrong attribute and reports it as missing, as the authentication case in “Two locations, two meanings” shows.
  • Aggregation depends on it. Counting how many interfaces across an estate still run a given protocol version is a routine migration question. It cannot be answered by grouping on inconsistent strings.
  • Sector vocabularies differ. The same interface may be named by a 3GPP reference point in one document and by its IETF protocol in another. Without a canonical protocol identity these do not reconcile.

The mapping therefore specifies the expected form for protocol type and version. An adapter normalizes what it receives before any rule is evaluated. Where a registry provides protocol identifiers, those are preferred for the same reasons they are preferred for algorithms.
