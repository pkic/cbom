Introduction

This section assumes no prior knowledge of bills of materials. It takes one product, one CBOM and one buyer's question, shows why the CBOM cannot answer the question, and shows what a profile does about it. Every other section elaborates on something that happens here.

A document that is correct and still unusable

A vendor supplies an nginx web server and, with it, a CBOM. Reading it, you learn that the product uses AES-256-GCM, X25519 and RSA-2048, that it holds a server certificate for example.com, and that the cryptography is implemented by OpenSSL 3.4.0. Every statement in the document is true.

Now the question you actually have to answer before you deploy it: when an administrator logs in to configure this product, what protects that session?

The document does not say. Not because the vendor was careless — the interface it described, it described well — but because nothing required it to describe that other one. A CBOM format specifies what may be recorded. It does not specify what must be.

components
  HTTPS service interface (TLS 1.3)     described in full
  AES-256-GCM, X25519, RSA-2048         the algorithms it uses
  example.com server certificate
  OpenSSL 3.4.0                         the implementing library

                                        (nothing about administrative access)

This is not an unusual document. It is the normal outcome of asking a supplier for a CBOM without stating what the CBOM is for.

Completeness depends on the question

The obvious remedy — ask for everything — makes the problem worse. A large product performs thousands of cryptographic operations, and a document that lists all of them buries the two or three facts on which any particular decision turns. Exhaustive coverage is not useful coverage.

There is no absolute standard of completeness for a CBOM. A CBOM is complete relative to a purpose. So the question worth asking is not "does this document contain everything", which has no answer, but "does it contain what this decision needs", which does — provided the decision has been written down first, in a form something other than a person can check.

A profile is that written-down form

A profile is a short list of rules stating which attributes a CBOM must carry to support one stated decision, for one stated reader. It is a minimum reporting requirement, not a schema and not a format.

The example used throughout this documentation is the Interface Disclosure Baseline. Its consumer is an operator or purchaser holding a product it did not build and cannot inspect. Its decision is whether the cryptography the product applies at its boundaries, including the interface used to configure it, is disclosed in enough detail to be recorded in an inventory and assessed against policy.

It has two kinds of rule. Product rules constrain the set of interfaces as a whole:

RuleRequirementLevel
P1The product declares at least one cryptographic interfaceMUST
P2The product declares at least one management (configuration) interfaceMUST

Interface rules then apply uniformly to every interface that has been declared: the protocol and its version, the key exchange, the encryption, the authentication, both endpoint roles, the interface type, the lifecycle stage the report describes, and the implementing library.

Eleven rules in total. That is the entire profile. It is short on purpose: it names the minimum that supports one decision and stops there, which is what makes it possible for a vendor to satisfy it and for a buyer to insist on it.

Note what the profile does not contain. There is no rule about whether the cryptography is any good. Whether a product is post-quantum ready is not a fact about the product; it is a judgement made against criteria that change over time, and it is kept outside the document in versioned policy. The CBOM carries facts. The policy makes the judgement.

What happens when the rules are run

Two nginx CBOMs, evaluated against that profile.

The first declares an HTTPS service interface and an SSH management interface, and describes both. It conforms.

The second is the document at the top of this page. Its HTTPS interface is described accurately and in full — every interface rule passes — and it fails, on P2, because no management interface was declared at all.

The failing document contains no false statement. It fails because conformance is measured against a decision rather than against truth. An accurate document that omits the one thing the reader needs is precisely the failure a profile exists to catch, and no check the format alone can perform will find it.

The Demo runs both of these, and a third, in the browser.

Withheld is not the same as missing

One refinement is worth meeting early, because it recurs throughout. In the conforming document, the management interface does not name its implementing library. It carries a marker saying the value is withheld. Rule I9 allows this: the attribute is required and withholdable, so the marker satisfies the rule where silent omission would not.

The distinction matters to whoever reads the document. A withheld value is a position the producer has taken deliberately and can be challenged in a negotiation. An absent value could be anything — unknown to the producer, not applicable, or simply forgotten. The first can be acted on; the second can only be guessed at. The methodology therefore distinguishes four outcomes for any attribute — supplied, withheld, unknown, undeclared — where the formats offer only present or absent.
