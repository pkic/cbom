APPLYING IT

Starting from a use case

A profile exists to support a decision. This page sets out what a use case is, why a profile has to start from one, and what follows for the CBOMs that answer it. The use cases the working group has identified, and its worked examples, are in the Use Cases section.

What a use case is

A use case is a consumer and a decision. The consumer is whoever reads the CBOM and has to act on it. The decision is a choice between stated actions, and it raises a small number of questions that the CBOM has to help answer. Three things are needed before a profile can be written:

  • The consumer, named by role: a buyer, a vulnerability responder, a migration lead.
  • The actions being chosen between. A decision answerable in only one way is not a decision, and a profile written from one has no principled place to stop.
  • The questions the consumer has to answer to choose. Step 3 of Method turns each into the facts a CBOM must carry.

A sector, a product category or a field a format offers is not a use case. Each can be the setting for one, and sector vocabulary belongs in the profile written for it.

Why the use case comes first

A profile answers the question "what must be disclosed so that a particular decision can be made", which is a different question from "what cryptography does this contain". The first question cannot be answered in the abstract. An attribute that is indispensable for one purpose is irrelevant to another: a vulnerability responder needs the implementing library and can ignore endpoint roles, while a procurement team checking an interface baseline needs the reverse.

Starting from the use case also bounds the disclosure. Without a stated purpose there is no principled way to decide where a profile stops, and the result drifts either towards demanding everything, which vendors reasonably resist, or towards a lowest common denominator that supports no decision at all. A profile with a named consumer and a named decision can be assessed on its merits.

One document, several profiles, and the limit

Different consumers can apply different profiles to the same unchanged CBOM. A supplier that produces one complete document may find it evaluated against a procurement profile by one customer and a vulnerability profile by another, with nothing republished in between.

That holds only while each profile selects from facts the document already carries. Some profiles add facts the baseline does not define: knowing which algorithms an interface uses today answers none of a migration planner's questions, so a migration profile adds capability facts rather than selecting among the existing ones. A document produced against the baseline cannot be evaluated against such a profile at all, because the facts were never collected. These are the depth and coverage axes of composition in Profile.

The practical consequence is that "supply a CBOM" is not one request. A buyer has to name the profile, and a supplier that has produced baseline documents has not met a migration request by producing more of them. The Use Cases section groups its use cases by this distinction, and by two others that follow from the same starting point: whether the producer is the supplier of a product or the operator of a system, and whether the reader relies on the document as evidence.
