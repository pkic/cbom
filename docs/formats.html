MAPPING

A single profile expressed in two formats

The profile is defined independently of any format. A mapping locates each attribute, and the interface count, within a concrete document. CycloneDX provides a native cryptographic model; SPDX 3.0.1 does not, so a CBOM is expressed in CycloneDX and referenced from an SPDX SBOM.

Representation of an interface

An interface (cryptographic relationship) is represented as a cryptographic-asset component with assetType: protocol. The product-level rules are evaluated by enumerating those components and counting them, including the number that carry interfaceType = management. There is no native object representing the set of interfaces; the count is derived.

Interpretation of the columns

In CycloneDX, the cryptographic assets (I1–I5 and the provider in I10) are represented in native fields, which is an area of strength for the format. The interface-level classifiers on which the profile depends — interfaceType (I7), endpoint roles (I6), lifecycle stage (I8), and PQC posture (I9) — have no native field and are carried in component.properties under the pkic:profile: namespace. The interfaceType attribute is what makes product rule P2 evaluable.

In SPDX, the absence of a cryptographic model in 3.0.1 means that most detail is obtained through the linked CycloneDX CBOM. The area of strength for SPDX is provider identity (I10): it identifies the OpenSSL and OpenSSH packages by packageUrl, which is the value cross-referenced against vulnerability feeds.

The edge gap

interfaceType and endpoint roles describe the interface itself — the edge — yet neither format provides an object that represents the interface. Both attach these attributes to the protocol asset. This is sufficient for the disclosure baseline, but it cannot represent a determination that belongs to the connection itself, such as whether a session negotiated a non-post-quantum group. Providing such an object is the objective of the working group's first-class attributed-edge model.

Normalization in CycloneDX 1.7

CycloneDX 1.7 introduces the Cryptography Registry, which assigns stable identifiers to algorithm families so that, for example, AES256 and AES_256_GCM resolve to a single identity. For I3, I4, and I5 a registry identifier is preferred where present; CBOMs authored to version 1.6 carry free-text names that are normalized at the adapter (see Versioning).
