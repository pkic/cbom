MAPPING

One profile, two formats

The profile is written format-independently. A mapping locates each attribute — and the interface count — in a concrete document. CycloneDX has a native cryptographic model; SPDX 3.0.1 does not yet, so a CBOM is kept in CycloneDX and linked from an SPDX SBOM.

Where an interface lives

An interface (cryptographic relationship) is a cryptographic-asset component with assetType: protocol. The product-level rules are answered by enumerating those components and counting them — including counting how many carry interfaceType = management. There is no native "interface set" object; the count is derived.

Reading the columns

CycloneDX carries cryptographic assets (I1–I5, I10) on native fields — its strength. The interface-level classifiers the profile depends on — interfaceType (I7), endpoint roles (I6), lifecycle (I8), PQC posture (I9) — have no native field and ride in component.properties under a pkic:profile: namespace. Crucially, interfaceType is what makes product rule P2 answerable at all.

SPDX lacks the crypto model in 3.0.1, so most detail is reached through the linked CycloneDX CBOM. Where SPDX is strong is provider identity (I10): it already names the OpenSSL / OpenSSH packages by packageUrl, which is what you cross-reference against CVE feeds.

The edge gap

interfaceType and endpoint roles describe the interface itself — the edge — yet neither format has an object that is the interface. Both pin these to the protocol asset. It works for this baseline, but cannot hold a verdict belonging to the connection itself (e.g. "this session negotiated a non-PQC group"). Closing that gap is the working group's first-class attributed-edge model.

Normalization in 1.7

CycloneDX 1.7 adds the Cryptography Registry, giving stable identifiers to algorithm families so AES256 and AES_256_GCM resolve to one identity. For I3/I4/I5 prefer a registry id where present; older 1.6 CBOMs carry free-text names normalized at the adapter (see Versioning).
