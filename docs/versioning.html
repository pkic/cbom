Handling older CBOM files

"Older" is ambiguous until you separate the versions that actually move. Three independent things carry a version, and each ages differently. A conformance claim must cite all three to be reproducible.

Three version axes

AxisExampleMoves when
Carrier formatCycloneDX specVersion 1.6 → 1.7the SBOM/CBOM standard revises
Profileinterface-disclosure v0.1 → v0.2the requirements change
Content revisiona product's CBOM version over timethe product or a re-scan changes

A freshly generated CBOM (new content revision) may still be serialized in CycloneDX 1.6 (old carrier) and evaluated against profile v0.2 (new rules). Conflating the axes is the usual mistake.

Carrier version bands

The profile declares an acceptance range, so older CBOMs are handled deliberately. The rules file says "appliesTo": { "cyclonedx": { "min": "1.6", "tested": "1.7" } } and the validator applies a four-band policy:

The validator prints the band it landed in. On the command line you can see all four by running against 1.7, a 1.6 copy, and a 1.5 copy of the example CBOM.

Supporting recommendations

  • Normalize at the adapter. Prefer CycloneDX 1.7 Cryptography Registry identifiers where present; for 1.6 free-text names, apply a versioned name-map before the rules run.
  • Upgrade over reject. Mechanically upgrade a legacy CBOM (bump version, attach registry ids, record provenance) rather than bouncing it — re-encode facts, never add them.
  • Pin the profile version in every conformance claim; tighten rules behind dated grace windows (emit a warning before flipping to fail).
  • Deprecate, don't delete, vocabulary. If interfaceType values change, keep old values recognized (mapped to their replacement) for at least one profile major version.
  • Track freshness & supersedence so an old content revision never silently means "wrong."
Full detail is in versioning-and-legacy-cboms.md, and the acceptance range is enforced by validate_cbom.py's format gate — see Files.
